# Tailscale / Surge Ponte 与高码率媒体传输

设计 v0.3，2026-11-12。当前建议优先验证原生libwebrtc，QUIC作为有条件备选，理由见[传输路线复核](传输路线复核.md)。以下是未来实施规格，没有改动本机Tailscale、Surge、路由、防火墙或账号设置，也未实测连接。

## 1. 外部隧道与产品连接分开

KKRemote接收可达端点并建立自己的认证媒体会话。Tailscale/Ponte负责设备网络可达性；不集成其VPN扩展、不复制其打洞算法、不要求它们同时运行。先分别验收两种网络配置；同时启用时的系统路由归属不作默认假设。

| Endpoint类型 | 用户输入 | KKRemote行为 |
|---|---|---|
| LAN | 本地发现或地址+端口 | Bonjour仅作同网便利，验证host身份后建立会话 |
| Tailscale | MagicDNS名称或tailnet地址+端口 | 保留原始名称，用系统解析与路由；不以mDNS发现作为前提 |
| Ponte | 用户选定Mac的`<name>.sgponte`+端口 | 保留hostname，经Surge当前接管路径解析和路由；不发送到自建公共DNS解析器 |

WebRTC候选的Host提供可配置的非特权TCP/TLS信令入口，交换能力、SDP和ICE候选；媒体使用受限范围内的UDP端口，通过BUNDLE/rtcp-mux尽量共享。具体范围、并发分配和Ponte映射在M0冻结，不假定每窗口一个端口。QUIC候选可使用明确的UDP服务端口。连接卡片显示实际入口；此处不预占声称已注册的产品端口。

HostID绑定公钥身份，endpoint仅是地址。首次配对经主机明确允许并核对身份指纹/短码；后续固定已验证身份，撤销后清除控制租约。外部VPN可达性不替代产品配对。身份握手采用标准TLS/已验证认证方案，认证信令绑定本次SDP/DTLS指纹，不自行发明密码学。

## 2. Tailscale接入

官方文档说明，无法直连时可能走DERP，带来额外延迟和吞吐限制；`tailscale ping/status`可辅助判断路径。不能把低RTT或100.x地址当作直连证据。[Tailscale性能诊断](https://tailscale.com/docs/reference/troubleshooting/poor-performance-tailnet)

WebRTC先使用所选覆盖网的host候选，不配置外部STUN/TURN服务，仍保留ICE的STUN连通性检查。需验证Mac/iOS网络枚举、socket路由与候选约束，不能悄悄改走未选择的物理网卡/公网路径。信令直接访问Mac上的TLS入口，不需要公网信令服务器。候选类型显示host/UDP不代表外层Tailscale直连。[ICE](https://www.rfc-editor.org/rfc/rfc8445.html)

产品状态区显示“所选接入方式：Tailscale”和KKRemote实测的RTT/可用速率；只有得到可信的外部诊断结果才标记direct/relay，否则写“隧道内部路径未知”。Mac可在用户触发诊断时检查可用CLI，iOS不依赖shell。CLI不可用不阻止正常连接，也不使用未文档化API抓取隧道内部状态。

官方当前文档记录Tailscale MTU为1280；因此不能把1500当作内层包尺寸默认值。[Tailscale MTU说明](https://tailscale.com/docs/reference/troubleshooting/network-configuration/tcp-connection-two-devices) 媒体包还需扣除IP/UDP及所选SRTP或QUIC开销；核对实际发包大小，避免套用另一后端的payload参数。

直连路径用于高码率资格测试；DERP/其他中继路径用于验证可用性与有界降级。用户仍可使用中继连接，但不要标成已达到高码率档。网络从中继变直连或反向变化时，依据会话反馈重新爬升/降低码率，不依赖一次启动测速。

## 3. Surge Ponte接入

Surge官方说明，Ponte服务端运行在Mac，设备通过由Surge处理的`.sgponte`名称访问，底层通道由Surge选择；其代理辅助穿透对UDP中继能力有条件。[Ponte官方说明](https://manual.nssurge.com/features/ponte.html)

这说明可以设计“Ponte端点”，但**尚不能据此证明任意用户配置上的WebRTC或QUIC媒体已经可用**。WebRTC的信令hostname可达，不等于其交换出的LAN IP/动态端口可达。M0必须验证ICE候选与外部端点映射、双向检查、DTLS、SRTP与DataChannel、高码率稳定性和切网恢复。先试受限端口范围及候选策略；必要时评估原生network/socket适配器，不能靠简单替换SDP地址宣称解决。[原生PortAllocator](https://webrtc.googlesource.com/src/+/refs/heads/main/p2p/base/port_allocator.h)

若WebRTC需广泛修改ICE核心或新增常驻媒体代理才能使用Ponte，再与QUIC固定服务端点对照。QUIC同样须验证名称、真实UDP、握手与stream/datagram。HTTP网页打开成功不足以通过任一媒体资格测试。

Surge的策略与全局设置可能阻断QUIC，且受版本影响。[策略参数](https://manual.nssurge.com/policies/parameters.html)、[全局参数](https://manual.nssurge.com/profile/general.html) 因此诊断应区分：Surge未接管/名称未解析、端点不可达、QUIC被策略拒绝、配对失败、链路不足。产品提供针对当前端点的操作说明，不默认改动全局配置或为了连通关闭所有QUIC策略。

Mac的系统HTTP代理设置不自动等于对任意原生UDP流完成接管；Ponte场景要按实际Surge接管模式验证。iOS同样通过实际系统网络环境验证，不假定一个SDK能绕过路由配置。

如果某种Ponte路径只允许可靠字节流，不把高码率视频偷偷塞进TCP后仍显示“低延迟模式”。首版可明确提示媒体路径不可用；是否提供可用性优先的兼容模式，由M0结果单独决定并标注较低的交互等级。默认不增设公网TURN，不根据一个超时自动切换两套媒体栈。

## 4. 优先候选：原生WebRTC媒体会话

每host一个PeerSession，内部先验证一个PeerConnection、多窗口video track和去重后的音频track。客户端新增/关闭窗口对应订阅和轨道生命周期，协商串行化，可评估少量轨道复用。不同主机独立连接，客户端另有总资源预算。

ScreenCaptureKit原生帧进入自定义source，VideoToolbox通过encoder/decoder factory接入，媒体使用SRTP/RTCP；不重复编码、不通过DataChannel传全部视频。libwebrtc负责媒体分包、网络反馈、pacer、协商的重传与恢复，KKRemote负责像素/颜色、窗口/输入、资源预算及端到端帧龄。默认ObjC工厂不等于已具备HEVC/HDR，需要M0实证。[媒体规范](https://www.rfc-editor.org/rfc/rfc8834.html)、[factory接口](https://webrtc.googlesource.com/src/+/refs/heads/main/api/video_codecs/video_encoder_factory.h)

DataChannel划分小型可靠有序控制（按下/释放、IME、窗口事务）与可覆盖状态（绝对指针、光标位置）。不可靠增量必须有累计/恢复语义。限制单消息与缓冲，禁止大文件占用输入通道。DataChannel的SCTP控制与媒体控制并非天然统一调度，必须测满载输入延迟。[DataChannel规范](https://www.rfc-editor.org/rfc/rfc8831.html)

TrackBinding绑定surface/generation/epoch与轨道身份；帧元数据将RTP timestamp对应到正确配置和布局。控制可靠有序不保证它与媒体帧相互有序，新epoch首帧后才原子切换画面和输入。具体元数据通路、resize与格式切换在M0验证。

网络估计由libwebrtc反馈给编码速率；KKRemote控制质量上限、可见性、帧率、允许的分辨率与硬件预算。不额外叠一套互相争抢的快速拥塞控制，不通过强制最低码率绕过拥塞。指标至少包含target/actual bitrate、pacer queue age、丢包/修复、解码与展示帧龄；可观测字段以所锁版本实际接口为准。

## 5. 有条件备选：QUIC连接结构

下述为QUIC候选的媒体工程规格，保留用于必要时对照；不是首版同时实施的第二套后端。

每host一个PeerSession，初始使用一条QUIC连接；控制stream、配置stream以及单个datagram flow由KKRemote进行逻辑复用。不同surface在应用头中携带标识，不假定Network.framework允许每个窗口各自创建一个独立datagram flow。当前本机SDK头文件明确每连接只能创建一个QUIC datagram flow；实施时还需核对最低支持系统与实际行为。

QUIC控制流处理配对、订阅、窗口动作和按键；datagram承载有时限的视频/音频及可覆盖的状态。控制与媒体共享连接不等于自动获得硬优先级，主机调度器在调用send前就限制媒体批量和总入队时间。首版不自行改QUIC拥塞控制算法。[Apple连接组](https://developer.apple.com/videos/play/wwdc2021/10094/)

QUIC DATAGRAM自身不提供可靠交付和帧级重组；其传输仍受拥塞控制。[RFC 9221](https://www.rfc-editor.org/rfc/rfc9221.html) 所以需要下述应用层媒体协议。

## 6. QUIC候选需要自建的分包、恢复与参考链

1. 编码器产生完整access unit，附surfaceID、streamEpoch、frameID、PTS、随机访问标记和配置版本。
2. 按传输层可用datagram尺寸切为应用层分片，每片包含总长度、序号、片数和有界头。不是依靠IP分片，也不是声称QUIC会把一个过大的datagram自动分片。
3. 初始试验媒体payload不超过约1000字节，并受协商上限约束；这是保守试验值，不是固定协议常量。发送失败/MTU变化时重新计算，不静默截断。
4. 接收端按epoch/frame重组，有字节、窗口数、总帧数和时间预算。小概率乱序留短暂窗口；缺片反馈走可靠控制或重复发送的恢复请求，并限频合并。
5. 仅在预估能赶上期限时选择性重发缺片；发送端保留短期有界缓存，过期即释放。具体重传次数和期限由M0丢包实验冻结。
6. 帧完整后才交给解码器。缺失参考帧且不可及时修复时，停止提交依赖链、申请随机访问帧，恢复后再继续；不把“丢旧帧”理解为可随意删掉压缩参考帧。
7. 大关键帧分批pacing，不集中瞬发；VideoConfig可靠确认后才能显示新epoch。连续关键帧请求限频，防止丢包触发码率爆炸。

以80Mbps/60fps为例，平均每帧约167KB，1000字节payload需要约167片；即使每片独立丢失概率仅0.1%，至少丢一片的帧比例也约15.4%。这是简化概率例子，现实丢包可能突发；它说明不能把“局域网丢包少”当作省略补片和参考链恢复的理由。FEC不是首版必做项，先衡量选择性补片与关键帧恢复的CPU、带宽和帧龄代价。

发送完成、网络收到、解码完成、呈现完成分别统计，不把QUIC ACK当作用户已看到该帧。

## 7. 两种路线共用的高码率与延迟预算

总体预算：媒体目标码率不超过用户设置、编码/解码能力、热预算、以及已测可持续净载荷能力所允许的最小值。初始保留约20%–30%链路余量供波动、关键帧、音频和控制，比例待测；应用、SRTP或QUIC及隧道开销另行计量，不能按网卡标称速度计算。

启动先发送首帧与温和码率，再依据短窗口反馈逐步提升；不要为等完整测速让窗口黑屏数秒。用户选择高画质是更高质量目标与上限，不是要求静态画面持续灌满带宽。

调节输入：编码耗时、发送queue age、缺片/修复比例、解码耗时、客户端展示间隔、热状态和可见窗口数量。网络与媒体预算反馈各司其职，防止重复快速调节。QUIC候选若没有公开内部BWE/RTT指标，使用应用层ping与确认反馈并标明含义；任一路线都不声称能读取全部内部数据。

背景窗口先降帧/暂停，前景保留原生像素。链路持续积压时调整码率与帧率；必要的分辨率变化走版本化协商。界面用“原生清晰度 / 实际帧率 / 当前视频码率 / 链路受限原因”说明状态，不展示不真实的满格高清标签。

## 8. 连接体验与诊断

首次连接：选择接入方式 → 输入/选择设备地址 → 认证配对与能力交换 → 建立媒体路径 → 窗口目录/订阅 → 首帧。已配对设备复用身份，重新连接不反复要求输入地址。信令、ICE/握手、首帧分别记录，避免一个“连接失败”掩盖具体环节。

保存一个host的多个endpoint，允许用户手动切换Tailscale/Ponte。第一版不在两个VPN之间自动切换系统设置；应用内切换端点时释放旧控制租约，新连接验证同一host身份后恢复订阅，避免双路重复注入。

故障提示应能区分：名称解析失败、信令超时、ICE无可用候选/媒体端口不可达、DTLS失败、QUIC策略阻断候选、身份不匹配、权限缺失、源窗口关闭、媒体格式不支持、网络带宽不足。无法区分超时和策略阻断时明确“待诊断”，不根据一次超时下确定结论。

诊断面板高级展开保存：endpoint类别、后端/上游revision、候选对或连接端点、测量RTT、payload大小、媒体/总流量、重组和修复率、排队时间、实际格式、route observation来源。iOS后台恢复、Wi-Fi切换、VPN暂停、Mac睡眠唤醒均走相同业务重连状态机，底层按实际ICE restart/连接重建能力适配。

## 9. 接入验收矩阵

| 组合 | 通过条件 |
|---|---|
| Mac→Mac，Tailscale；iPad/iPhone→Mac，Tailscale | 名称/IP两种入口；配对与窗口流；受控直连路径达到所选性能档；中继可解释降级 |
| Mac→Mac，Ponte；iPad/iPhone→Mac，Ponte | `.sgponte`原生解析/路由；所选后端真实UDP媒体与双向输入；候选/端口或策略问题可诊断；合格路径达到性能档 |
| 两种方式分别切换/重连 | 重新验证同一host身份、无双控制、无粘键、旧epoch数据失效 |
| 小包可达、大帧失败 | MTU/分包诊断能区分；首帧大关键帧不会永久卡住 |
| 高码率持续20–30分钟 | 主机发送与客户端解码无无限队列，散热降档和链路降档可区分 |

各项当前状态均为待实施验证。没有基于用户已安装软件推定其现有隧道配置已经满足要求。
