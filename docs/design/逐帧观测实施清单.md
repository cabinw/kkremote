# T02：逐帧时间与丢弃原因

2026-11-13。**T02a–d 已实现并完成本阶段诊断验收。** 开销、故障恢复与静态边界见 [T02d 实测](../testing/通信方案v1验收.md)；物理显示延迟仍未验收。 发送端记录见 [T02a](../testing/发送端逐帧诊断.md)，RTP 关联、15mac LAN / Ponte 对照与关键帧优化见 [T02b](../testing/RTP与桥接逐帧诊断.md)，解码 / 应用显示队列和 iPhone 蜂窝复测见 [T02c](../testing/接收解码与显示逐帧诊断.md)。

发送端按精确 RTC 包装对象身份关联源帧与编码输入；RTP 通过至少三个 absolute-capture-time 锚点验证恒定偏移，不以事件相邻时间猜测。帧事件 32,768 条、RTP 分组 4,096 个，默认关闭，停止桥接后批量导出。噪声前置筛帧已定位到 WebRTC FrameDropper；真实窗口的周期尖峰定位到大关键帧发包。HEVC 周期由约 2 秒调为约 10 秒（按帧数），保留按需关键帧与丢包恢复。

## 实施前缺口（保留作对照）

| 环节 | 已有观测 | 需要补齐 |
|---|---|---|
| `WindowCaptureSource` | 完整 / idle / invalid 计数，捕获 PTS，回调间隔、WindowServer age | 会话内递增 frame ID；把非 complete、时间戳重复、色彩不符分别记原因；记录交给 WebRTC 的时刻 |
| `EncoderTelemetry` | 输入与输出按 RTP timestamp 暂存匹配，编码耗时与大小的区间统计 | 保留有界逐帧事件；关联 capture PTS；超过期限未匹配仅记 unknown，不直接判编码器丢帧 |
| `HEVCEncoder` | 同步提交错误、正常输出 | VT 异步 status、frameDropped、空 sample、Annex-B 失败目前直接返回，需分别记录；区分编码丢弃与 WebRTC 提交前适配 |
| `DatagramBridge` | 总体排队 / 超期 / 溢出 / socket 错误计数 | 每帧首末包入队与出队、包序号间隙、队列 oldest age 与峰值；避免复制媒体载荷或逐包同步写盘 |
| `HEVCDecoder` | WebRTC 汇总解码耗时、帧数 | decode 输入与 VT 回调时刻；解析、参数集、建会话、解码异步错误原因 |
| `FrameCounter` | 独立 renderer 回调次数、间隔 P95 / max | 加入帧关联键；明确这是 WebRTC 渲染回调，不是应用最终显示 |
| `SampleBufferRenderer` | received / enqueued / replaced / backpressureDrops / failures 内部计数 | 将计数接入报告；保存主线程等待、latest 替换和 enqueue 时刻；格式 / sample 创建失败也要计数 |

当前 `FrameCounter` 与真正的色彩管理 renderer 是两个观察者。SDK 的零丢帧不能排除应用 `latest` 替换或显示层背压；`enqueue` 也不能被命名为“屏幕呈现”。

## 关联与时间口径

1. 每个媒体引擎分配独立 epoch，帧 ID 只在其内递增。当前换窗重建引擎，源代次由此隔离；未来若支持引擎内换源 / resize，必须显式增加 source epoch。
2. 捕获事件保留 `capturePTSns` 与本机 monotonic callback 时间；编码输入保留 `RTCVideoFrame.timeStampNs` 和 32 位 RTP timestamp。
3. 桥接只解析经过长度校验的 RTP 明文头部，以 `(session, SSRC, timestamp)` 分组，并保留 PT、sequence、marker。先从协商结果区分媒体 / RTX / 控制，不能只按字节位置猜包种类。SRTP 加密的 RTX 原始序号不在该层强行解析。
4. 验证编码 timestamp 与发包 timestamp 是否一致；若 SDK 引入偏移，必须建立并验证映射，不能靠相邻时间猜测后声称完整关联。无法关联的阶段明确输出 `unknown`。
5. 接收端使用自己的 monotonic 时钟。跨机器时间不能直接相减；先报告各端局部间隔，RTT 与时钟校准误差另列。物理端到端延迟仍属于 T06。
6. RTP timestamp 回绕、同一帧多包、重传、同 timestamp 重复到达、断开重连都必须覆盖；不能把网络晚到直接当成解码失败。

## 实施顺序

- **T02a 主机观测**：捕获 → 编码提交 → VT 异步结果，增加明确失败原因和有界事件缓存；不改编码参数或媒体格式。先做本地回环及观测开 / 关的开销对照。
- **T02b 包与队列（已实现）**：关联 RTP 头部、桥接入 / 出队和丢弃原因，验证 timestamp 映射。保持 NACK/RTX/PLI 和现有加密方式；预编译 SDK 的 pacer enqueue 未直接暴露，编码输出到桥接首包仍是组合区间。
- **T02c 接收与显示队列（已实现）**：解码输入 / VT 回调、WebRTC renderer 回调、主线程等待、最终 enqueue 与替换已接入 schema 3 trace / schema 9 报告。显示 observer 与轨道代次分开，精确 RTP 关联，碰撞和缺失标 unknown。USB 构建 9 完成 2 秒 / 10 秒 / 2 秒关键帧对照与 350 秒关闭 trace 的蜂窝 Ponte 测试；未更新 TestFlight。
- **T02d 验收（已完成）**：已关联一次大关键帧间隔和一次普通帧的 103.51 ms 收包展开，未发现相应解码 / 显示队列长积压。已完成受控丢包下的真机 NACK/PLI 恢复、严格静态源和多次重连、off/on/on/off 观测开销实验。未见帧率回退，CPU 增量明确保留；SDK 内部状态不能确定的继续标注 unknown。物理显示延迟仍归 T06。

事件缓存应有明确容量和溢出计数，媒体线程只写轻量记录；由后台线程批量导出。默认关闭逐包细节，诊断模式显式开启。报告不包含窗口标题、输入内容、配对信息或媒体载荷。

验收包含正常流、受控丢包、重连和静态源。观测开关需要相同条件 A/B，确认不会因日志本身制造帧间隔。iPhone 本地安装与内部 TestFlight 分发分别记录；本清单不触发重新签名、上传或改变现有配对。
