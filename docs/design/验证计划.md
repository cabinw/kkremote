# KKRemote 验证计划

这是设计v0.3的未来执行清单；本轮没有执行这些运行时实验，没有开发或安装 KKRemote。A的Apple原生方向保留，原生libwebrtc优先验证，QUIC有条件对照。当前优先窗口串流，整屏与多主机暂不实施；阶段归属见[实施计划](分阶段实施计划.md)。

## 先固定比较条件

以同一主机、客户端、显示器、测试内容和网络比较 Jump、Casement 和未来 KKRemote。记录版本、物理/虚拟显示器模式、逻辑分辨率、像素尺寸、缩放、codec、色度、位深、码率和实际连接路径。没有确认这些变量时，不能把“更清晰”归因于某一个算法。

推荐设备覆盖：Apple silicon Mac 主机；Mac 客户端分别连接普通 SDR 与支持 HDR 的显示器；一台 HDR 能力已确认的 iPad/iPhone 和一台普通 SDR 设备。不能仅凭设备名称猜 HDR/硬解能力，需记录系统报告和实际创建解码器的结果。

网络使用局域网基线和Tailscale/Ponte各自的实际媒体路径，再按 RTT 10/30/80/150 ms、丢包 0/0.1/1/3%、带宽 10/30/100/200 Mbps 分组；无需穷举所有组合，优先基线、高码率、小量丢包、受限带宽与切网。网络模拟环境及双向/单向设置必须记录。独立记录Tailscale直连/中继证据来源与Ponte接管/QUIC策略，无法获知内部路径时标未知。[接入矩阵](网络与媒体传输.md)

## 开发前必须做的验证

| 编号 | 问题 | 操作与需要保留的结果 | 决策 |
|---|---|---|---|
| S1 | 单窗口实际拿到哪些内容 | 测普通窗口、sheet、菜单、右键菜单、独立弹窗、窗口遮挡/最小化/移出屏幕；记录frame状态、过滤器和contentRect | 决定独立窗口捕获是否足够，是否需要关联surface |
| S2 | Retina是否真实 | 同一1000×700pt测试窗放在1×/2×显示器，检查真实源/输出像素；窗口跨显示器时复测 | 验证源精度，不把上采样当高清 |
| S3 | HDR全链路是否成立 | HDR测试内容，记录采集pixel format/色彩附件、codec profile、解码输出、显示headroom；对照SDR回退 | 失败时定位到单环节，不能只观察“更亮了” |
| S4 | resize与坐标是否同步 | 旋转、键盘弹出、Split View、连续缩放与HDR/SDR切换；记录requestId/layoutRevision/streamEpoch/首帧及输入映射 | 验证尺寸/格式事务，拒绝旧帧与过期输入 |
| S5 | 输入与焦点边界 | 同进程多窗及相同标题/几何、公开API的SCWindow↔AX窗口匹配、前后台切换、拖拽出窗、修饰键、中文输入；检查up事件恢复 | 匹配歧义限制操作/进入只读；首版不依赖尚未实现的整屏回退 |
| S6 | 主机虚拟画布是否值得采用 | 后续选用V时再测：创建/销毁、HiDPI、HDR、睡眠唤醒、显示器拔插、异常恢复 | 当前不执行；和客户端多主机画布分开 |
| S7 | 原生媒体后端能否满足格式与网络要求 | 优先验证libwebrtc的VT factories、HEVC/Main10、帧元数据、恢复/队列、Tailscale候选与Ponte端口映射；必要时同源同codec对照完整基本媒体机制的QUIC | 三类客户端真实媒体；HDR与小量丢包恢复通过；可维护适配；不得只测H.264静态首帧 |
| S8 | 高码率是否保留低延迟 | 约1080p/1440p/4K三档按20–120Mbps区间试验，记录净载荷、总流量和各阶段排队 | 以实际像素和可持续能力分档，不以手机/平板名称固定降采样 |
| S9 | 移动边缘/留白几何是否正确 | 分开远端外框、可信裁切、本地chrome、safe area、键盘与内容rect | 不靠固定裁顶部解决布局；正确性先验收，最终视觉后续优化 |

测试图包含黑白小字、彩色小字、1像素红蓝细线、渐变、棋盘和移动区域。全部使用自建内容，便于对齐源像素与远端输出。HDR显示可先做像素/元数据一致性验证；要声明亮度与色彩准确性，还需合适的显示测量条件。

## 传输选型的公平对照

先完成原生libwebrtc最小闭环；出现明确瓶颈时再做QUIC对照，不同时生产化两套后端。固定捕获源、像素、codec/profile、VideoToolbox设置、GOP与测试序列。独立记录后端内部自动丢帧/缩放行为；如果比较中自动变更画质，该轮不能只按延迟宣布胜负。

先做编码后网络段对照，再做完整交互；网络段不能代替真实多窗口resize和输入到显示。分别测首帧、20–120Mbps爬升/稳定、0.1/1%丢包及突发丢包、带宽骤降与恢复、MTU、大关键帧、一个活动窗与多个后台窗、媒体满载输入、30分钟热状态。P50/P95/P99、冻结时间、修复开销和实际图像一起评估。

Tailscale host/UDP候选不证明外层direct；Ponte TLS/HTTP成功不证明ICE/SRTP可达。记录所选候选/端口、原生socket接管条件、来源可查的外层路径。QUIC若仅有不恢复丢包的发送演示，不算与WebRTC等价。最终决策门槛见[传输复核](传输路线复核.md)。

## 建议验收目标

这些数字是待确认的产品预算，**不是两款软件的测量结果，也不是KKRemote已经达到的性能**。

| 维度 | 初始目标 | 量测方法 |
|---|---|---|
| 交互延迟 | 同网60fps、约2560×1440负载下，输入到可见反馈P95≤80ms | 外部高速拍摄/光学对齐；时间戳用于拆段诊断，不能单凭未同步两端时钟得端到端值 |
| 捕获交付后的处理与编码 | capture callback→encoded callback初始预算P95≤20ms | 单机monotonic时钟；另验证sample PTS与host-time映射，才能量完整capture frame age，不能将本项当作完整采集延迟 |
| 媒体积压 | 稳定运行时队列不持续增长；过期帧有明确计数 | 每阶段队列深度、oldest frame age与drop reason |
| 触点映射 | 稳态几何计算误差≤1源像素；旋转/resize无旧布局误投递 | 栅格目标+输入日志+截图坐标，对边缘与letterbox逐点验证 |
| 静态文字 | 原生像素尺寸下，黑白/彩色小字对照评审；不能只用PSNR判断 | 1:1裁片、OCR辅助、边缘/色度误差；将肉眼评审与客观值并列 |
| 拖动与滚动 | 长拖拽、快滚动无粘键、无双重手势；正常释放有匹配up | 记录有限状态机与reliable输入序号，注入断连/失焦 |
| HDR回退 | HDR→SDR映射无明显截断/洗白，不支持能力时明确回退 | 已知渐变/色块+附件检查；按可用条件测显示输出 |
| 稳定性 | 30分钟窗口切换、尺寸变化与弱网场景无崩溃、泄漏式增长、无法恢复的黑屏；整屏切换留后续 | 资源曲线、session事件、关键帧请求/超时记录 |

## 移动平台场景

优先验证三类真实工作流：编辑代码与终端、浏览器/文档、含菜单和复杂工具栏的桌面应用。iPhone竖屏应选择可操作的局部视口或合理最小窗口尺寸；不能为了填满屏幕把桌面UI压成不可读的布局。

直接触控：tap、长按、拖动、两指滚动、本地pinch、取消手势。触控板：相对移动、加速度、轻点/拖拽、右键、滚轮。硬件输入：iPad鼠标、外接键盘、Command组合键、输入源切换。软键盘：中文marked text、提交、删除、候选、隐藏与焦点变化。

Mac客户端：单host多窗口时输入控制权；本地⌘Tab与远端快捷键分配；多窗口切换与关闭行为；本地/远端光标不重复；剪贴板操作方向可理解。整屏/窗口并存与多host全局焦点留到相应后续阶段。

## 必须保留的诊断字段

hostId、sessionId、surfaceId/generation、layoutRevision、streamEpoch、frameSequence、capture/encode/send/decode/present各阶段时间戳及其时钟域、实际像素尺寸、contentRect、codec/profile、color description、帧大小、关键帧、drop原因、RTT/loss估计、queue age、输入序号/控制租约与按钮状态；额外记录后端与上游revision、track/MID/SSRC及帧时间戳映射、endpoint类别、候选对、MTU/payload、路径观察来源、修复率与thermal状态。字段仅在当前实现确实可观测时填写，不伪造未知值。

诊断默认记录指标和事件类型，不记录真实窗口内容、输入文字或密码。测试内容使用固定样本，保证问题可复现。尺寸和网络降级的原因要能解释，避免出现“开启了高清但不知道为什么仍糊”的情况。
