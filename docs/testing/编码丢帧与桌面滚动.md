# 编码丢帧定位与桌面滚动验证

2026-11-13，继续排查 1440p、20 Mbps、60 fps 目标下的降帧。新增编码提交计数后，确认原始噪声的主要帧数损失发生在进入原生编码器之前。用户随后选择先验证桌面/滚动内容；新的合成桌面源在两分钟本机回环中达到 60 fps，原 TestFlight 构建 5 经异地 Ponte 接收成功，用户反馈“60fps 流畅”。

本轮增加诊断与明确标注的新测试负载，没有把噪声目标宣告达标。当前未实现真实窗口捕获或远程输入。

## 定位到的边界

`encoderDetails.submittedFrames` 记录进入 `RTCVideoEncoder.encode` 的次数，可与源产帧、编码完成和发送累计计数一起计算区间速率。它包含返回错误的提交尝试，需结合 `submissionErrors`、未匹配输入和回调计数解释。

同机固定 UDP v2/socket 的 35 秒原始噪声对照，排除前 10 秒：

| 阶段 | 实际速率 |
|---|---:|
| 测试源 | 60.00 fps |
| 进入编码器 | 12.48 fps |
| 编码完成 | 12.44 fps |
| 解码完成 | 12.44 fps |
| 视频有效载荷 | 19.03 Mbps |

提交错误与回调拒绝均为零，最后只有一个编码输入尚待回调；接收端零 RTP 丢包、零 NACK，但 SDK 全会话记录 12 次冻结，接收缓冲区间均值约 98.90 ms。这说明即使没有异地网络丢包，此负载的降帧与不均匀帧到达也已经存在。

新增 `scripts/probe-encoder.sh` 绕过 PeerConnection、带宽估计和发送器，直接把相同测试源送入同一原生 H.264 编码器。12 秒原始噪声测试设置 20 Mbps、1440p60，排除前两个采样后，编码约 **60.04 fps / 158.49 Mbps**，QP 为 51、提交与编码计数均为 719、提交错误为零。它是编码器输出字节率，不是网络吞吐，也未验证解码质量。

因此，当前源与编码器组合在 20 Mbps 设置下严重超出预算，接入实时发送链路后大量输入帧未进入编码器。它支持“编码输出与码率预算不匹配导致帧率受限”的解释；具体 WebRTC 内部丢帧分支尚未逐项归因。上游的 [VideoStreamEncoder](https://webrtc.googlesource.com/src/+/refs/heads/main/video/video_stream_encoder.cc) 与 [编码码率调整器](https://webrtc.googlesource.com/src/+/refs/heads/main/video/encoder_bitrate_adjuster.cc) 可用于理解这些机制，但这些 main 分支资料不是所用二进制的精确源码映射。

探索了显式帧时长、常量码率、空间 QP 调节、速度优先与低延迟模式等配置，未获得同时满足原始噪声 60 fps 和 20 Mbps 的方案，未采用到生产路径。普通模式仍明显超出码率；低延迟模式在该输入下主要表现为编码器内部丢帧。参数被 API 接受不能代替输出验证。相关语义见 [Apple 数据率限制](https://developer.apple.com/documentation/videotoolbox/kvtcompressionpropertykey_dataratelimits) 和 [低延迟编码模式](https://developer.apple.com/documentation/videotoolbox/kvtvideoencoderspecification_enablelowlatencyratecontrol)。

## 桌面式滚动负载

新增 `--pattern desktop`，界面名称为“桌面 / 滚动内容（合成对照）”。画面持续显示 SYNTHETIC 标签，包含静态侧栏、白底文档、深色代码区和局部动画图表。文档速度在 180–660 像素/秒间连续变化，代码区为 180 像素/秒；不采集用户文件或桌面。

文字和文档栅格只在初始化时生成，逐帧执行裁剪滚动与小范围图形绘制，复用现有四缓冲上限。没有缩小输出像素或改写噪声生成器。新增模式只改变发送源，不改变配对、信令、固定 UDP 或 H.264 协议；构建 5 无需理解新的模式名称即可接收其视频。

### 两分钟本机回环

2560×1440、60 fps 目标、20 Mbps 上限，固定 UDP v2/socket、interactive pacing。排除前 10 秒后：

| 指标 | 结果 |
|---|---:|
| 源 / 提交 / 编码 | 均约 60.00 fps |
| 接收解码 | 60.00 fps；所有秒级 fps 样本为 60 |
| 实际视频码率 | 3.73 Mbps |
| 编码耗时区间均值 / P95 | 7.80 / 8.00 ms |
| 解码耗时区间均值 / P95 | 1.89 / 1.99 ms |
| 接收缓冲区间均值 / P95 | 12.50 / 12.99 ms |
| SDK 全会话冻结 / RTP 丢包 / NACK | 0 / 0 / 0 |

20 Mbps 是上限；可压缩的滚动文字无需填满它。本轮不证明该链路已承受持续 20 Mbps 视频，不代表任意桌面、照片或视频内容都能达到相同帧率。上述为同机回环，也不能替代异地延迟或实际显示测量。

完整指标和直接编码器报告见 [脱敏数据](data/2026-11-13-encoder-desktop-summary.json)。

### 构建 5 异地 Ponte 复测

用户确认原构建 5 已显示新滚动画面，并反馈“60fps 流畅”。随后连续采集主机约两分钟，合并实时快照得到 125 个样本、首末跨度 123.999 秒：

| 主机侧指标 | 结果 |
|---|---:|
| 实际编码尺寸 / 格式 | 2560×1440 / H.264 High 5.1 |
| 源 / 编码提交 / 编码完成速率，计数差 | 均约 60.00 fps |
| 编码 fps 秒级样本 | 59–60，均值 59.19 |
| 视频有效载荷码率，样本均值 / 最大 | 3.69 / 5.09 Mbps |
| 发送等待，区间均值的平均 / 最大 | 0.051 / 6.043 ms |
| 控制 RTT，样本平均 / P95 / 最大 | 16.38 / 19.46 / 21.39 ms |
| NACK / PLI / 重传包增量 | 0 / 0 / 0 |
| 控制 probe 超时增量 | 0 |

编码帧累计增加 7,440 帧，除以观察时间约为 60 fps；秒级 SDK 字段存在窗口与取整差异，不能以其 59.19 均值替代累计计数吞吐。主机应用桥接没有队列丢弃或发送错误，累计最大队龄约 0.891 ms。

这确认了当前合成桌面滚动内容在原构建 5 上的异地可用性，并有用户对 60 fps 流畅的确认。接收端 JSON 尚未取得，不能据主机计数声称零接收冻结、给出接收抖动缓冲，或把控制 RTT 当作视频端到端延迟。原始噪声仍保留为未达标压力项。

## 复现与验证

```bash
scripts/build-lab.sh mac-release

# 不连接网络；观察请求 20 Mbps 时编码器的真实输出。
scripts/probe-encoder.sh 20 12 noise > /tmp/encoder-noise.json

# 本机真实编解码与媒体链路；不是远程网络测试。
python3 scripts/benchmark-media.py --rates 20 --duration 120 \
  --resolution 2560x1440 --pattern desktop --bridge-transport socket
```

本轮完成 Mac Release 构建与签名检查、直接编码器探针运行、35 秒噪声定位、120 秒桌面式滚动编解码回环，以及测试画面导出检查。没有发布新的 iOS 构建；手机继续使用构建 5。原始噪声的严格 1440p60/20 Mbps 目标仍未通过，后续应保留它作为独立压力项，并扩展真实内容和画质测量。
