# 显示模式自动变化排查（2026-11-14）

本次已经确认显示配置的调用方：00:33 的虚拟屏移除来自 Jump；其后六次实际分辨率 / 刷新率变化由 `UURemoteServer` 发起。两次 `DisplaysExt` 调用对应本会话经用户同意恢复 60 Hz 的操作。用户没有主动调整显示，与以下程序行为并不矛盾。

这解释了相关长测的显示条件变化，**不等于已经解释或修复 Ponte 的全部到包尖峰、约 31 fps 的捕获现象或内存增长**。本轮仅调查日志并补充文档，没有修改远程工具设置、停止其服务或启动新的长测。

## 为什么无人手动调整仍会变化

UU 每次切入较大分辨率后约 0.8–1.0 秒开始自己的 ScreenCaptureKit 捕获。三次停止捕获后，恢复 mode 55 的间隔几乎完全相同：

| UU 最后停止捕获 | UU 提交恢复 mode 55 | 间隔 |
|---|---|---:|
| 00:39:54.587 | 00:40:22.679 | 28.092 秒 |
| 01:16:57.148 | 01:17:25.242 | 28.094 秒 |
| 01:32:37.216 | 01:33:05.318 | 28.102 秒 |

**推断：UU 的远程捕获生命周期在开始时套用显示模式，停止后延迟恢复旧模式。** 这比“用户在设置中反复调整”更符合记录，也解释了为何已经恢复 60 Hz 后，稍后分辨率仍会再次变化。

能够直接证明的是调用进程、目标 mode、捕获启停与时间关系；尚未证明具体由哪个控制端、自动重连还是客户端设置触发。UU 自有连接日志为封装格式，本轮没有解密或修改其配置。因此不能把上述推断写成已核实的某个 UI 开关行为。

本次 47.95 / 59.94 Hz 变化伴随明确的软件 modeset 和分辨率变更，不能解释成 ProMotion 的正常逐帧刷新调节。一次显示模式选择同时包含像素尺寸和刷新率，并非只改变远端视频分辨率。

## 对复测的处理

1. 长测前先让其他远程工具结束会改变源显示的捕获会话，并等待至少 45 秒，使已观察到的约 28 秒恢复动作先完成；再确认两次源守护采样一致。45 秒只是针对本次已观察行为的等待余量，不是所有软件的保证。
2. 如果必须保留 UU 观看，需要先核对其控制端设置，让会话保留被控 Mac 当前显示模式，并验证连接、断开都不改变它。当前尚未核对或修改该设置。
3. 待外部恢复动作完成后再按已授权条件设定 60 Hz、确定窗口尺寸，先测原始供帧，再启动 3600 / 300 历史容量 A/B。源守护持续有效；模式改变即保留报告并将该轮作废。
4. 不在长测中循环强制改回 60 Hz。与另一程序反复争用显示模式会制造新的停顿，破坏冻结与内存归因。

只读复查命令（按实际事件时间缩小范围，不收集无关应用内容）：

```bash
/usr/bin/log show --start '2026-11-14 00:30:00' --end '2026-11-14 01:40:00' \
  --style compact --info --debug \
  --predicate 'eventMessage CONTAINS "SLSCompleteDisplayConfigurationWithOption" OR (process == "WindowServer" AND (eventMessage CONTAINS "client api - modeset" OR eventMessage CONTAINS "desired mode change"))'
```

没有查到提交日志时只能标为未知，不能依据某个 App 正在运行或收到通知就归因。日志保留期限有限，发生事件后应及时提取。
