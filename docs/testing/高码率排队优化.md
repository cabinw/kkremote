# 高码率排队优化：双 Mac LAN / Ponte

2026-11-12，M0 合成视频传输实验。发送端为 Apple Silicon Mac，接收端为 Intel MacBookPro11,4（macOS 15.8.1）。本轮只处理传输与测量；窗口体验、Tailscale、HEVC/HDR 和公网连接不在验证范围。

## 本轮改动

### 减少一次媒体发送需要处理的 UDP 包

旧版 `fixed-udp-v1` 的 UDP payload 上限为 1232 字节，头部和认证占 64 字节，单片只能装 1168 字节。实际观察到的 SRTP 包大量落在 **1201–1248 字节**，因此不能按“WebRTC 的 RTP 包约 1200 字节”计算封装预算。旧版通常把一个媒体包拆成两个外层包，增加了加解封装、调度、重组和丢包恢复的工作量。

`fixed-udp-v2` 使用 16 字节头部、16 字节 AES-GCM tag 和最多 1248 字节内层数据，最大 UDP payload 为 **1280 字节**。初始实验仍使用 1232 字节上限时，分片问题没有消失；扩大到上述实际观测需要的大小后，复测中不再产生媒体分片。v1 继续保留为显式兼容模式，双方必须选择一致版本，不会静默降级或改走 LAN ICE。

v2 的头部包含版本、方向、包类型、分片序号、总长度和 64 位序列号；分片归属由首片序列号确定。每次会话使用随机媒体密钥，通过认证信令发送；HKDF 按会话、方向、协议版本派生独立密钥。GCM nonce 由方向密钥对应的递增序列号形成，禁止计数回绕。头部作为 AAD 认证。内层仍是 WebRTC 的 ICE/DTLS/SRTP/SCTP。

两端进入媒体会话前，必须通过**完整 1280 字节、带认证的双向 UDP 探测**；小包成功不能代替大包成功。探测确认建连时能够交付该大小的 UDP payload，不能证明沿途没有 IP 分片，也不能证明持续吞吐。Tailscale 等具有不同 MTU 的路径尚未验证，不能据此宣称兼容。

### 调整 WebRTC 的发送节奏

固定的 M157 SDK 中，屏幕内容默认的 `WebRTC-ProbingScreenshareBwe` 参数为 `1.0,2875,80,40,-60,3`。前两项分别是 pacing factor 和队列排空时间目标。SDK 没有暴露对应的 ObjC 单会话设置，因此当前通过进程初始化时的 field trial 设置，保留三个可复测档位：

| CLI `--pacing` | factor | 排空目标 | 用途 |
|---|---:|---:|---|
| `upstream` | 1.0 | 2875 ms | 上游默认对照 |
| `interactive` | 1.5 | 60 ms | 较快排空，可能加重链路突发 |
| `smooth` | 1.1 | 60 ms | 较平缓的发送节奏 |

当前默认使用 `interactive`，`smooth` 保留为对照。两者的 Ponte 重复测试波动明显，尚不能据单次结果确定生产参数。参数只在首次创建 WebRTC factory 前设置，进程内不能切换。**60 ms 是排空目标，不是硬性丢弃期限或整体延迟上限。** 没有关闭拥塞控制，也没有强制最低发送码率。应用侧仍保留原有的有界队列与 25 ms 等待期限；它们不约束 OS、Surge 或 WebRTC 内部的所有队列。

该默认参数可在所用二进制的字符串中核对；解析与应用机制参考 [WebRTC ALR 配置](https://webrtc.googlesource.com/src/+/refs/heads/main/rtc_base/experiments/alr_experiment.cc) 和 [VideoSendStream 配置](https://webrtc.googlesource.com/src/+/refs/heads/main/video/video_send_stream_impl.cc)。这些上游页面会变化，升级 SDK 时必须重新检查参数与实际行为。

### 观察编码突发，保留通过实测的编码路径

为每个会话独立创建 encoder factory，并在原生 H.264 编码器外增加观测：WebRTC 分配码率、请求帧率、单帧大小 P95/最大值、提交到编码回调的 P95、编码字节数、关键帧与未匹配回调数。记录样本数量有界，不保存图像。未匹配回调可能来自编码器内部丢帧，不能直接当作硬件排队深度。

以下实验没有改善综合结果，已从交付代码移除：

- 根据编码字节债务在输入侧丢新帧：带宽估计与帧率互相影响，Ponte 压测降至约 7.6 Mbps / 4 fps。
- 自定义 VideoToolbox `EnableLowLatencyRateControl`：在本机高复杂度源下，输入 60 fps、硬件输出约 30 fps，单帧增大；Ponte 进一步下降。明确最大 QP、单层帧率与实时帧率后仍未解决。这只说明本次实现与负载的结果，不能推论该 Apple API 在所有内容上都不好。
- 给原生编码器预留 10% 分配码率：本轮未观察到可重复的改善，Ponte 80 Mbps 档测得约 51.6 Mbps / 44.2 fps，因此不纳入交付。链路也存在时间波动，这一结果不能单独证明该策略必然更差。

因此当前继续使用原生 H.264 编码器，通过减少分片和调整 WebRTC pacing 降低编码突发造成的排队。没有丢弃已编码的参考帧，没有以降分辨率掩盖吞吐不足。后续编码器工作仍需解决动态码率下降时的帧大小响应；Apple 低延迟模式的能力与配置参考 [官方说明](https://developer.apple.com/videos/play/wwdc2021/10158/)。

## 测量口径

- 1920×1080，60 fps，H.264 SDR，确定性的高复杂度噪声源；保留真实编码/解码尺寸，关闭分辨率自适应。码率参数是上限，不保证实际填满。
- 两台 Mac 顺序测试，每次新建连接。LAN 使用原生 `direct-ice`；Ponte 使用填写的 `.sgponte` 地址和固定 UDP 路径。Surge 独立诊断确认本轮为 Ponte LAN 通道，不是公网或中继测试。
- 早期对照每次 40 秒，最终矩阵每次 60 秒；各端排除前 10 秒后统计。不同时间段的网络波动不能消除，单次更好的结果不是稳定性保证。
- 视频 Mbps 是接收端 WebRTC 统计的媒体字节速率，不是物理网卡总速率。固定 UDP 总字节、分片、丢弃和重组另有计数。
- `发送等待`、`解码耗时`、`抖动缓冲`先用累计统计的差分算出每个采样区间的均值，再对这些均值取 P95，**不是逐帧延迟的 P95**。
- `控制 RTT` 是 DataChannel 回声；它不等于视频单向延迟或输入到显示的延迟。CLI 接收端有真实解码和帧回调，但不是物理屏幕的光学测量。
- `viewerPassed` 只代表测试结束时视频与控制仍持续工作，不代表达到了性能目标。冻结、丢包和实际帧率必须一起检查。

## 实测结果

先看 80 Mbps 档的改动对照。以下均为 1080p60 噪声源，延迟单位为 ms，P95 口径见上文。

| 配置 / 时长 | 实际 Mbps | 实际 fps | 发送等待 P95 | 控制 RTT P95 | 抖动缓冲 P95 |
|---|---:|---:|---:|---:|---:|
| LAN 原生 ICE，上游 pacing，40 s | 73.50 | 60.00 | 3.30 | 12.51 | 15.94 |
| Ponte v1，上游 pacing，40 s | 40.21 | 37.26 | 1432.40 | 27.95 | 536.31 |
| Ponte v1，仅改 interactive，40 s | 36.21 | 31.45 | 26.16 | 431.33 | 161.36 |
| Ponte v2 + interactive，40 s | 71.47 | 58.45 | 5.13 | 44.28 | 90.92 |
| Ponte v2 + interactive，60 s | 60.41 | 51.12 | 6.92 | 26.05 | 126.66 |
| LAN 固定 UDP v2 + interactive，60 s | 74.08 | 59.88 | 2.05 | 15.02 | 83.17 |

**只加快排空并不能解决问题**：v1 的发送等待下降，但吞吐、控制 RTT 和冻结反而更差。减少包数量以后才同时改善吞吐和发送等待。也不能只取 v2 的 40 秒最好结果：60 秒复测仍明显波动。

`smooth` 的同批 60 秒矩阵如下。每次运行都验证两端可执行文件 SHA-256 一致：

| 路径 / 上限 | 实际 Mbps | 实际 fps | 发送等待 P95 | 控制 RTT P95 | 抖动缓冲 P95 |
|---|---:|---:|---:|---:|---:|
| LAN 原生 ICE / 80 Mbps | 73.40 | 59.98 | 2.52 | 12.07 | 34.56 |
| Ponte v2 / 80 Mbps | 51.97 | 45.53 | 20.76 | 27.18 | 136.70 |
| LAN 原生 ICE / 120 Mbps | 107.89 | 59.90 | 4.48 | 12.96 | 49.41 |
| Ponte v2 / 120 Mbps | 53.42 | 46.96 | 20.07 | 30.80 | 129.59 |
| Ponte v2 / 45 Mbps | 42.31 | 39.69 | 18.76 | 23.55 | 100.25 |

另一次相同 `smooth` / Ponte 80 Mbps / 60 秒测试达到 70.06 Mbps、57.65 fps，但发送等待 P95 13.29 ms、抖动缓冲 P95 152.35 ms。吞吐和接收缓冲不会必然一起改善。

最终使用默认 `interactive` 配置、最终 Release 二进制，增加一轮较长的 Ponte 测试：

| 上限 / 时长 | 实际 Mbps | 实际 fps | 发送等待 P95 | 控制 RTT P95 | 抖动缓冲 P95 | 全程冻结 |
|---|---:|---:|---:|---:|---:|---:|
| 80 Mbps / 120 s | **66.89** | **54.66** | **5.43** | 31.19 | 100.93 | 4 |
| 120 Mbps / 60 s | 65.04 | 51.31 | 9.48 | 154.90 | 178.17 | 2 |

两轮的应用侧发送队列丢弃、分片和重组超时均为 0，但 RTP 仍有丢包与 NACK。120 Mbps 档的控制 RTT 长尾也明显变差；当前不应靠继续提高码率上限改善体验。80 Mbps 的两分钟结果比短测更能暴露剩余问题。

验证已完成：信令认证与错误密钥拒绝；v1/v2 认证、跨版本拒绝、篡改与重放、分片重组边界；完整大小探测准入；Mac Release、iOS Simulator 构建；原生 ICE、固定 UDP v1/v2 的真实编解码自检。最终远端仍为 Surge 诊断确认的 Ponte LAN 通道。构建中保留了所用 SDK 全局 field-trial API 的弃用警告，升级 SDK 时需迁移到可用的 factory 配置入口。

完整脱敏指标、运行标识和可用的二进制哈希见 [JSON 汇总](data/2026-11-12-queue-summary.json)。丢包与冻结是全程累计值，测试时长不同，不能直接比较绝对丢包数来计算丢包率。

## 当前结论与后续工作

WebRTC 发送端的秒级积压已经显著改善，但不能宣布 Ponte 高码率低延迟通过验收。LAN 直连可达到约 108 Mbps / 60 fps；Ponte 的码率、帧率、重传与接收缓冲仍存在波动，且固定 UDP 适配器的接收缓冲也高于原生直连。上述测量不足以把所有剩余延迟都归因于 Surge。

后续仍优先处理底层链路：

1. 对齐发送、适配器入出队、接收和渲染的逐帧时序，加入可校准的输入到显示测量；当前的秒级均值不足以刻画长尾。
2. 在同一 pacing、相同包率与相同内容下重复 LAN 原生、LAN 固定 UDP 和 Ponte 三组测试，结合受控丢包、限速、负载变化分辨拥塞与调度问题。
3. 评估从 libwebrtc 源码接入固定端点 socket，减少现有 loopback + Network.framework 桥接中的复制与调度；先做可回退的对照，不直接更换协议。
4. 编码器重点验证码率下调响应、关键帧突发和硬件回调；新策略必须同时满足画质、码率、帧率和延迟，不能只看发送队列变短。

窗口体验与 Tailscale 继续后置。默认测试码率仍为 25 Mbps，不因某次短测成功就将 80/120 Mbps 设为已验证的工作档。

## 复现

```bash
scripts/test-signaling.sh
scripts/test-media.sh
scripts/build-lab.sh mac-release
scripts/build-lab.sh simulator

python3 scripts/benchmark-remote.py \
  --ssh viewer-mac \
  --remote-app /Users/your-user/KKRemoteLabTesting/KKRemoteLabMac.app \
  --host sender.sgponte --network 'Surge Ponte' \
  --route fixed-udp-v2 --pacing smooth \
  --resolution 1920x1080 --fps 60 --mbps 80 --pattern noise --duration 60

# LAN 对照：将 host 改为发送端 LAN 地址，并使用以下选项。
# --network LAN --route direct-ice

python3 scripts/summarize-lab.py .build/remote-bench/RUN_ID
```

两端先部署同一 Release 应用；远程脚本会检查可执行文件 SHA-256 一致，并在私有输出目录保存 manifest。配对密钥只经已有 SSH 通道传输，测试结束清除。原始日志、地址、配对文件与完整诊断不提交 Git；公开报告只保存脱敏指标。没有修改系统 VPN、Surge、Tailscale 或防火墙配置。

TestFlight 构建 2 不包含本轮修改；远程 iPad 仍需后续新构建与真机复测，不能用本轮 Mac 数据代替。
