## 可重复素材与口径

真实 Chrome 窗口捕获，固定四面板确定性 SVG 图纸、3× 平移缩放，源每面板 2048 个器件；并准备滚动文档、原生 60 fps 视频和严格静态页面。源窗口 1681×1084 点、2× 像素，等比适配到 2560×1440。HEVC 输出是 Main10 PQ；图纸和混合压力源本身是 SDR，不能冒充 HDR 亮度母版。真正 HDR 影片与灰阶验收另有既有实机记录。

20 Mbps 是编码预算，实际有效载荷单独报告。H.264 同源校准 16.71 Mbps / 60 fps，HEVC 约 13.25 Mbps / 60 fps；不加 padding 来制造满载。详情见[素材校准](真实负载素材校准.md)。

平均 fps 由稳态计数差 / 单调时间计算，排除开始出帧后的前 5 秒。freeze / framesDropped 是 SDK 累计值；primary RTP 丢包计数与 RTX 恢复分开，不能直接解释成永久损失。帧间隔是应用回调或显示 API 提交间隔，不是物理屏幕延迟。不同进程不直接相减裸时钟。

## 长时间测试

严格静态源 40 秒：60.01 fps / 0.335 Mbps，capture complete 2964、idle 0。去掉网页计数 DOM 更新后仍持续完整回调；暂不通过内容散列或任意筛帧隐藏该事实。静态带宽较低，但静态省电仍有优化空间。

首次 15mac LAN 轮次的共享浏览器窗口中途切到其他标签，随后 Ponte 轮次也被立即停止；两轮均标为无效并保留原因，没有纳入结果。重测改用独立窗口并每 10 秒核对身份和尺寸。身份校验是离散采样，不是逐帧内容证明。

独立窗口的第一轮有效 LAN 900 秒未通过：H.264 46.83 fps / 17.10 Mbps、2 次 SDK freeze（最大回调间隔 944.7 ms）；前四分钟约 60 fps，后段约 42 fps。Host 捕获 complete 回调后段也只有约 41–43 fps，接收端没有独立累积丢帧。Ponte 后续诊断 122 秒同样约 41.85 fps / 17.68 Mbps，因排查源端而提前结束，不算 15 分钟验收。

当时系统实际处于 ProMotion（系统报告 120 Hz），不是原固定 60 Hz 测试条件。已按用户此前授权暂时切回固定 60 Hz，先做短测再长测；不能靠复制帧把低更新的源包装成 60 fps。该失败保留，不能直接断言所有 ProMotion 内容都会降帧，仍需分清浏览器绘制与 WindowServer 捕获节奏。

固定 60 Hz 后未置前的短测为 31.00 fps，捕获 complete 同样约 31 fps，且零丢包 / NACK / 冻结；单改刷新率并未解决，不能把 ProMotion 定为已证实根因。继续对照窗口前台 / 遮挡状态。

追加排查排除了单纯 SVG 绘制、H.264 / HEVC 分支和桥接影响：同内容预栅格化仍约 30.81 fps；Main10 本机同源约 30.79 fps。独立 `CaptureCadenceProbe` 完全不接编码器或网络，仍约 31 fps；queueDepth 3→5、换另一扇 HDR 浏览器窗口都没有恢复。

USB 投屏窗口开 / 关复核提供了更明确的环境证据：同一窗口、固定 60 Hz、raw SCStream，Device Hub 可见时约 31 fps，关闭后 59.80 fps，重新打开又是 31.02 fps。说明这台机器上的可见投屏预览会干扰捕获节奏；尚未单独区分其窗口遮挡、合成或系统调度机制，不推广为所有设备的必然行为。正式长测只用 USB 启动与复制报告，连接后关闭 Mac 的投屏预览，手机 App 继续保持前台。预栅格化参数作为诊断保留，长测恢复原 live SVG 负载，不以降低素材复杂度达标。

旧窗口身份守护还带来了独立观测开销：反复启动 AppKit / ScreenCaptureKit 查询进程，Host 在 280 秒对照区间编码 59.386 fps；同一会话换成常驻 CoreGraphics 元数据探针后，87 秒区间为 59.988 fps，捕获 complete 同步改善。此轮明确作为中途改动的诊断，保留完整 Host 会话；结束时主动终止本任务远端 Viewer，因此没有最终 Viewer 报告，也不计为 15 分钟通过。正式长测统一使用轻量探针。原始捕获与守护方式的脱敏数据见[捕获诊断](data/2026-11-13-transport-v1-capture-diagnostics.json)。

固定 60 Hz、关闭投屏预览、常驻元数据守护的正式 LAN 900 秒已通过：15mac 解码 59.986 fps / 17.726 Mbps，SDK freeze / framesDropped / RTP 丢包均为 0；首末五分钟 59.973 / 59.985 fps。接收缓冲区间均值的 P50 / P95 为 2.194 / 7.287 ms，最大渲染回调间隔 169.2 ms。两端 thermalState 均为 nominal；接收端首末五分钟 footprint 中位数增长约 4.45 MiB，Host 下降约 0.45 MiB。完整身份守护通过。该结果支持固定条件下的持续吞吐，不代表所有单帧均匀呈现或已测物理延迟。

正式 Ponte realtime 900 秒为 59.981 fps / 16.604 Mbps，零 RTP 丢包与解码丢帧，但 1 次 SDK freeze，所以严格零冻结门槛失败。约第 40 秒出现 171.4 ms 回调间隔，同一接收样本的桥接探测 RTT 为 145.7 ms，解码均值 5.54 ms / 解码回调 P95 5.82 ms，生产桥接无积压。此轮未开逐帧 trace，不能精确分配到网络、Surge 或远端调度，也不能直接相减双端时钟。编码目标区间曾降到 3.215 Mbps、稳态中位数约 18.672 Mbps；完整平均值保留这一段。

因此追加同素材 adaptive 900 秒对照以验证等待代价，但第一轮因显示环境变化作废；第二轮在新环境完成，详见下文。手机的后续长测因锁定未执行。完整脱敏结果见[长测数据](data/2026-11-13-transport-v1-long-runs.json)，短轮故障恢复不能代替这些门槛。

## 物理端到端延迟

没有独立高速拍摄 / 光学传感器对源屏幕和接收屏幕进行同步采样，本轮 T06 不予通过。USB 投屏引入额外路径，不能用它测手机真实显示延迟；RTT、抖动缓冲和 enqueue 也不是替代值。

### 显示环境中途变化

adaptive 的追加轮次在约第 431 秒被守护停止：窗口从 1681×1084 变为 1550×1058 点；随后系统报告当前屏幕为 Jump Desktop Display 1，3184×2176 像素、1592×1088 逻辑点、120 Hz。该轮无完整 Host 报告，作为环境变化的无效轮次保留，不能拿前七分钟替代十五分钟。后续测试按当前显示环境另列，不覆盖现有 Jump 显示设置，也不把不同显示环境的差值归因于单一播放参数。

新 Jump 显示环境的 Main10 本机 40 秒校准只有 41.15 fps / 13.01 Mbps，零 RTP 丢包；原始探针 SDR 两轮约 59.93 / 60.43 fps，HDR 约 50.98 fps。HDR queueDepth 5 / 8 / 3 的后续短探针分别约 48.03 / 52.81 / 55.19 fps，未证明加深队列有效，生产仍保留 3。因为探针已绕过编码与网络，这组结果不能归咎于 Ponte 发送队列；还没有把虚拟显示器的 HDR 合成与并发负载独立分开。此条件暂不能宣称真实 HDR 高复杂度窗口稳定 60 fps。

新环境下另一次完整 adaptive 900 秒：两端约 47.56 fps / 17.50 Mbps，1 次 SDK freeze、零 RTP 丢包和解码丢帧，发送队列无积压；捕获计数同步下降，不能判为 60 fps 档通过。接收缓冲区间均值 P50 / P95 约 69.2 / 183.1 ms，说明加等待也没有修复源端供帧，不能仅把 adaptive 当作通用修复。

新环境的滚动源 Main10 40 秒为 39.848 fps / 13.416 Mbps；同一窗口切到原生 60 fps 视频后为 60.000 fps / 5.597 Mbps、零 SDK 冻结与 RTP 丢包。这说明结果与内容和捕获负载相关，不能泛化为 Jump 虚拟显示完全不支持 60 fps。视频素材本身是 SDR，输出使用 Main10 PQ，不能由该片段验证 HDR 高光母版。

完整 H.264 回环的捕获池 3 / 5 / 5 / 3 对照（每轮 40 秒）分别 40.204 / 40.270 / 40.182 / 40.209 fps，未见收益，默认保留 3。新增 `--capture-depth` 仅为本地诊断入口，并将实际深度写入 captureDetails。查阅固定 M157 的[H.264 原生编码路径](https://webrtc.googlesource.com/src/+/95554e4a0c5c343fdc989387d9d0ce18e2a2294b/sdk/objc/components/video_codec/RTCVideoEncoderH264.mm)，未裁剪的原生缓冲可直接交给 VT；不在缺乏证据时把问题说成必然的整帧 I420 拷贝。

iPhone 后续启动被 iOS 明确以 Locked 拒绝，用户确认当前不在设备旁边。没有启动新的手机 15 / 30 分钟测试，前面完成的 60 秒故障抽查仍有效；不能将 Mac 或回环测试冒充手机结果。USB 启动失败时现在会清理本轮 Host / 守护，避免占用原测试端口。
