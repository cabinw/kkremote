# T02a：发送端逐帧诊断

2026-11-13。通信侧的第一段逐帧链路：**捕获回调 → 提交 WebRTC → 编码器输入 → 编码输出 / 明确失败**。默认关闭，不改变编码参数、媒体格式、Ponte 桥接或客户端交互。

本次不是发送排队优化完成，也不代表整个 T02 通过。RTP 发包与桥接队列、远端解码、应用显示提交仍分别属于 T02b / T02c；物理端到端延迟属于 T06。

## 实现与口径

- 新增 `FrameTrace`：每个 Host `PeerEngine` 独立 epoch；当前每次换窗会重建引擎，因此也隔离捕获源。环形缓存上限 32,768 条，覆盖历史的数量单独报告；源身份和编码输入跟踪各最多 120 个槽位。
- 记录只含单调时间、帧序号、PTS、编码器 RTP timestamp、字节数和有限原因。没有视频载荷、窗口标题 / 标识、地址、配对信息或输入内容。
- 媒体回调只追加内存记录。显式 CLI 诊断在停止媒体后拍快照，在 utility queue 编码并原子写盘；CLI 等待导出结束后退出。不会逐帧写盘。持续运行且尚未结束的会话不自动落盘，强杀进程可能丢失内存记录。
- `WindowCaptureSource` 将 idle、非 complete、无效 sample / PTS / buffer、重复或逆序 PTS、HDR 格式不符分开计数。idle 不是丢帧。
- HEVC 区分异步 VT status、`frameDropped`、空 sample、Annex-B 转换失败；同步提交失败和 WebRTC 拒收另列。此次没有人为触发真实 VT 硬件错误；原因计数的受控测试不冒充硬件故障复现。
- 两秒后没有结果、跟踪容量不足、时间戳冲突、重置未匹配以及输出缺少输入记录都属于 **unknown**，不能相加声称实际编码或网络丢帧。H.264 使用原生 SDK，其内部主动丢帧没有公开逐帧原因。
- 报告 schema 8 新增原因计数和 trace 摘要；信令 / 媒体线上的格式不变。`--frame-trace-dir` 只影响 CLI 诊断，iOS UI 无需接入，也没有安装或发布新手机包。

## 为什么不用捕获时间戳直接配对

首次 HEVC 回环中，某源帧 PTS 为 `179303039867375 ns`，编码输入变成 `179303039874000 ns`。SDK 调整了时间戳，按相等或最近时间来配对都不足以证明是同一帧。

当前使用新建的 `RTCCVPixelBuffer` **包装对象身份**：源端登记弱引用，编码入口验证同一个对象，输出再按有界 RTP 输入表匹配。不持有像素缓冲，不改变缓冲池压力；对象地址不写入文件。探针 718 帧均通过精确身份关联。后续如果 SDK 复制包装对象、裁切或转换造成身份变化，该路径输出 unknown，不降级为时间邻近匹配。

源 PTS、编码 PTS 和本机事件时间分别保留。输出里的 RTP timestamp 是编码器交给 SDK 的值，尚未证明与线上 RTP 头相同。跨设备时间没有直接相减。

## 验证结果

10 轮各 30 秒，2560 × 1440、目标 60 fps、20 Mbps 上限；固定 UDP v2 / socket 的**单 Mac 回环**。HDR、SDR 各按 off / on / on / off 对照；表中帧率、码率排除最初 5 秒，CPU 秒包含整次进程的源、编解码和本机接收。逐帧 P95 使用整段保留事件，与区间统计的 P95 不混用。

| 场景 | 观测 | 接收平均 fps | 实际视频 Mbps | 进程 CPU 秒 |
|---|---|---:|---:|---:|
| 合成 HDR 渐变 · hdr-1-off | 关 | 60.00 | 0.284 | 2.509 |
| 合成 HDR 渐变 · hdr-2-on | 开 | 60.00 | 0.280 | 2.378 |
| 合成 HDR 渐变 · hdr-3-on | 开 | 60.00 | 0.280 | 2.105 |
| 合成 HDR 渐变 · hdr-4-off | 关 | 60.00 | 0.280 | 2.407 |
| 合成 SDR 滚动 · desktop-1-off | 关 | 60.00 | 3.713 | 13.235 |
| 合成 SDR 滚动 · desktop-2-on | 开 | 60.00 | 3.738 | 13.252 |
| 合成 SDR 滚动 · desktop-3-on | 开 | 60.00 | 3.708 | 13.201 |
| 合成 SDR 滚动 · desktop-4-off | 关 | 59.92 | 3.742 | 13.241 |
| 真实 Chrome HDR 窗口 · hdr-window-on | 开 | 60.20 | 0.432 | 3.461 |
| H.264 噪声边界 · noise-on | 开 | 12.85 | 19.134 | 9.445 |

- 短测没有观察到开启记录引起的帧率或进程 CPU 回退；两次重复不足以给出严谨的开销置信区间，也不声称 CPU 数字下降代表优化收益。
- 真实窗口：1,787 个编码输入全部精确关联并输出；源提交到编码入口 P95 **0.0535 ms**，编码回调 P95 **5.2075 ms**，直接测得源提交到输出 P95 **5.2593 ms**。这些只覆盖已进入编码器的帧，不包括网络、解码或显示。
- 真实窗口捕获了 5,325 个 complete 帧，但只有 1,787 个进入编码器。记录了 3,537 次包装对象在进入编码器前释放，与 RTCVideoSource 限制 60 fps 的路径一致；具体内部丢弃策略没有探针，仍标 unknown。不能把这些帧算作 VT 或网络丢包。捕获过量也是后续减少无效工作的候选方向。
- 噪声稳定段只有 **12.85 fps**，实际约 **19.13 Mbps**。源端提交 1,801 帧，387 帧进入编码器、387 帧输出，1,414 帧未进入编码器且包装对象释放。编码回调 P95 **9.86 ms**；未看到同步 / 异步失败。SDK `qualityLimitationReason` 全段为 `none`，表明这个汇总字段不足以解释前置筛帧。
- 噪声中一次输出间隔 **319.45 ms**：前后可关联的源帧 ID 为 17 → 36，编码入口间隔 **318.01 ms**，当前帧从源提交到编码入口 **0.065 ms**，编码回调 **8.90 ms**。中间源帧没有进入编码器。这里的“前后源帧间隔”只比较两张最终输出的帧，**不等于源停止产生帧 318 ms**。这段证据把低帧率范围定位到编码器入口之前，尚不能指定 SDK 内部函数或具体丢弃原因。
- 噪声的平均发送延迟 **21.64 ms**、平均接收缓冲 **37.19 ms**，SDK 冻结计数 5；本机回环已复现问题，不能归因于 Ponte 专有路径。帧级发送队列还需 T02b。
- HDR / 滚动 / 当前真实窗口实际只约 0.28 / 3.7 / 0.43 Mbps；噪声虽接近 20 Mbps，却未达 60 fps。因此 **持续 20 Mbps、60 fps 的真实高负载验收仍未通过**。

矩阵的编码输入全部有精确身份，事件缓存无覆盖。两轮结束边界各有一次 callback rejected；矩阵版本没有停止标记，不能进一步断言其原因。随后补入停止标记、时间戳冲突隔离和 schema 8，最终版本另做回归，见下面记录。完整数值见 [脱敏 JSON 摘要](data/2026-11-13-sender-frame-trace.json)；原始 trace / 日志保留在本机沙盒 `Data/TransportTrace/`，未加入公开仓库。

最终版本验证：

- Mac Release、iOS 通用设备 Release 编译通过；iOS 只编译，未安装、上传或分发。已有 Host 进程及手机配置保持运行。
- 并发环形缓存 / 覆盖数量、弱引用不占用像素缓冲、媒体代次隔离、RTP 回绕 / 重复时间戳隔离、明确错误与 unknown 区分、分析器拒绝时间邻近猜测的检查通过。
- 20 秒真实 HDR 窗口：1,189 次编码输入 / 输出，最后一秒 SDK 报告 61 fps（统计窗口取整），SDK 冻结 0、RTP 丢包 0；停止边界已入 trace。
- 20 秒噪声：292 次编码输入 / 输出，末尾 13 fps，SDK 冻结 1；前置筛帧仍可复现。这一项只通过诊断链路检查，**没有通过 60 fps 性能验收**。
- 20 秒受控丢包 HDR：Host 注入 19 个丢弃数据报，接收 RTP 丢包计数 19、NACK 8、SDK 冻结 1；末尾恢复 60 fps。此项证明诊断在恢复期间仍可工作，**不代表丢包恢复已达零冻结要求**。桥接 `localSocketDrops` 与 RTP 丢包口径不同，未将二者合并。
- 最终三个 trace 都含停止标记，均未覆盖缓存。矩阵和最终二进制 SHA-256 分别保留在 JSON 中，区分结束边界 / 冲突隔离补充前后的验证范围。

这些是共用开发机上的短测，原 Host 进程保留；尚未做新代码的 iPhone / 15mac 长测、真实 Ponte 压测或静态源验收。T02 保持进行中。


## 重现

用独立 DerivedData 构建 Mac App，沿用仓库的开发签名与沙盒权限；不要覆盖正在服务手机的 Host。自检随机使用本地端口，不绑定原手机测试端口。

```bash
bash scripts/test-frame-trace.sh
python3 scripts/benchmark-frame-trace.py \
  --app .build/TransportTrace/Build/Products/Release/KKRemoteLabMac.app/Contents/MacOS/KKRemoteLabMac \
  --directory "$HOME/Library/Containers/com.cabinw.kkremote.lab.mac/Data/TransportTrace/new-matrix" \
  --duration 30
```

可加 `--window-id` 指定已获授权捕获的真实窗口；它仅用于本地测试，不写入摘要。矩阵对 HDR 渐变、SDR 滚动各按 off / on / on / off 顺序运行，再跑可选真实 HDR 窗口与噪声边界。期间不并发编译或运行其他性能基准。

单轮可以在原有 CLI 命令增加 `--frame-trace-dir <沙盒可写目录>`，媒体结束后生成 `sender-<epoch>.json`。解析方式：

```bash
python3 scripts/analyze-frame-trace.py <sender-epoch.json> --output <analysis.json>
```

分析器按明确帧身份关联，输出逐帧间隔的 P50 / P95 / max 和最长编码输出间隔对应的源、编码入口、编码回调记录。窗口边界、缓存覆盖、未匹配尾部保留为未知。它不从 RTT 推算单向延迟，也不把 WebRTC renderer 回调当作屏幕呈现。
