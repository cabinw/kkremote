# Duo 单窗口体验与真机验证

2026-11-23，代码基线 `38da1fb`。首轮要回答两个问题：在 Duo 的不同屏幕姿态下，Mac 窗口边角的控件能否看全、点准；连续滚动时，手机发出的动作和最终显示的文字是否跟手。此篇记录方案和开发环境预检。Duo 的画面、操作、HDR 及稳定性尚待真机验证。

## 真机预检

| 层级 | 本次观察 | 对下一轮的影响 |
| --- | --- | --- |
| 线缆、信任、通信 | USB 枚举得到一部 iPhone。Lockdown 读取 iOS 27.3 成功，配对验证通过。CoreDevice 对同一设备报告 wired、paired，主动查询详情后隧道为 connected | 可以通过 USB 与手机系统通信 |
| 开发者服务 | macOS 27.2.1、Xcode 27.2、iPhoneOS SDK 27.2。手机回报开发者模式关闭。查询显示信息时，系统明确因开发者模式关闭拒绝挂载开发磁盘。Xcode 检查未发现新的硬件支持组件 | 在手机「设置 → 隐私与安全性 → 开发者模式」开启，重启、解锁并确认后再查 DDI 和显示信息。若仍失败，按新的底层错误定位 |
| 编译、签名、安装资格 | KKRemoteLab 的 generic iOS Debug 编译与开发签名构建均成功，产物签名校验通过。本次选用的开发描述文件未覆盖该 Duo。按实际构建的 bundle ID 查询，手机未装此客户端 | 在开发团队下确认设备注册情况，选用或生成覆盖该设备的开发描述文件，再校验并安装基线。登记状态本次未查开发者后台 |
| 客户端与媒体 | 既有视口几何测试通过 2,403 项断言。尚未在 Duo 启动客户端，也未观测首帧、输入或视频实际路由 | USB 用于安装和观测。串流基线优先走现有 LAN 配置，以真实会话单独验证，后续再对照 Ponte |

复核时先用 `idevice_id -l` 在本机选择 USB 设备，使用 `idevicepair validate` 核验信任。对同一设备执行 `xcrun devicectl device info details`、`ddiServices`、`displays`（各带 `--device <本机目标>`）。核对开发签名、描述文件覆盖情况后安装并启动 KKRemoteLab。记录布尔结果、构建号、系统版本和失败层级；设备标识、描述文件、原始日志及截图留在本机。开发者模式操作见 [Apple 说明](https://developer.apple.com/documentation/xcode/enabling-developer-mode-on-a-device)。

### 单窗口边角与输入

1. 先定位裁切层。用两角带编号按钮、四边有标记的合成窗口，对照源窗口、解码画面和实际屏幕。现有 iPhone 渲染会对选中窗口按源坐标约 20 pt 加圆角遮罩。分别检查源内遮罩、iOS 安全区、显示缩放以及设备的物理圆角，记录消失的第一个环节。源内遮罩剪掉的按钮要先修遮罩；手机截图也需与真机可见范围对照。[窗口渲染](../../Apps/TransportLab/Sources/IOSLabView.swift) · [既有圆角验证](iPhone正式链路界面接入.md)
2. 在当前视频容器坐标内求有效安全矩形，扣除外层已经留出的边距。窗口已完整可见就沿用原布局。有余量时优先最小平移；平移仍会遮挡时等比缩小，像素精确模式同步复核。折叠、旋转、键盘和文本焦点变化时重算。首轮按实测屏幕尺寸与安全区布局；没有稳定姿态信号时用显式触控板入口。
3. `ViewportGeometry` 统一产生内容矩形，视频、光标、点击、拖动和文字定位共用同一正反变换；安全边距内的触点不发送给 Host。窗口切换期间按窗口代次丢弃陈旧输入。对于编码前已经缺失的弹出菜单，单独验证随窗口出现的附属界面。[视口几何](../../Apps/TransportLab/Sources/MobileInteraction/ViewportGeometry.swift) · [渲染容器](../../Apps/TransportLab/Sources/MobileInteraction/MobileViewport.swift)
4. 仅当完整窗口方案明显损失阅读面积时，再试「工具栏独立内缩」。只对能可靠定位顶部边界的窗口启用，并验证弹层锚点；贯穿顶栏的侧栏、自绘标题栏和无法定位的控件沿用完整窗口方案。

### 实验顺序与判读

| 次序 | 同条件对照 | 记录和通过依据 |
| --- | --- | --- |
| 0 · 基线连通 | 安装基线，验证启动、现有 Host 目录、选择物理窗口、首帧及一次可逆点击。区分开发隧道与媒体路由 | 保存构建、实际画面尺寸、fps、编解码、SDR/HDR、首帧耗时和回执。收到可识别画面且点击命中正确窗口后，开始交互对照 |
| 1 · 形态与圆角 | 外屏竖横、展开屏竖横、半开；记录实际可用姿态。每个形态测试标题栏两角、浏览器标签、WPS 工具栏、键盘开合以及切换中旋转 | 记录容器/安全矩形、源尺寸、缩放、偏移与触点映射。编号目标完整可见、点中相同编号，边缘空白不误触，关闭键盘后回到原视图 |
| 2 · 滚动 | 同一个物理窗口、同一长文、同一 LAN，先固定 60 fps、码率档、尺寸和显示模式。A 为当前构建，B 仅改发送节奏，C 在 B 上加惯性。每种慢拖、快甩、反向及再触打断交替做 10 次 | 统计首个增量等待、Host 事件间隔、呈现帧间隔 P50/P95、长停顿和误触。惯性只启动一次、打断后无残余滚动；同时报告样本数和 CPU。网络 RTT 单列。触摸到出光另做高速摄影 |
| 3 · 切换与键盘 | 最近窗口和现有选择器对照；同应用两窗来回切换，半开时输入中文，再旋转并收起键盘 | 操作次数、首个可交互帧、焦点窗口、中文提交次数；切换时无错窗输入，键盘收起后目标仍可点 |
| 4 · 画质与 HDR | 输入方案固定后，再单独比较固定画质与滚动降开销。长文停在细字处；播放已知 PQ 片源，分别检查桌面显示与 HDR 原始显示。高刷只在设备实际支持且报告后单列 | 记录运动/静止帧龄、恢复细字耗时、丢帧和冻结。分别核对采集、解码格式及渲染路径。Duo 亮度与持续高刷待实测，截图不能量化峰值亮度 |

每轮用相同源窗口和媒体路由交替跑基线与候选版本。若出现掉帧，分开查看输入等待、捕获、编码、网络和呈现，再决定该改哪一层。最终记录每种姿态通过与失败的操作、复现条件和脱敏汇总。可复用 [几何测试](../../scripts/test-ios-viewport.sh)、[逐帧诊断](接收解码与显示逐帧诊断.md)、[物理延迟测量](物理画面延迟测量规程.md) 和 [既有 Main10/PQ 验证](HEVC-Main10-HDR验证.md)。
