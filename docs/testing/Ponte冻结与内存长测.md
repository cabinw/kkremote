## 冻结已经定位到哪里

早期有效 90 秒诊断 `f69fa269dcf8` 捕获一次 213.46 ms renderer 间隔。用同一 SSRC / RTP 时间戳匹配前后两帧，并核对两端完整主流包序号集合：

| 观测阶段 | 相邻帧间隔 / 当前帧耗时 |
|---|---:|
| 发送端首次交给 OS | 17.40 ms |
| 接收桥接首次收到 | 202.93 ms |
| 接收桥接最后一个主流包到达 | 相邻帧间隔 213.27 ms |
| 当前帧解码回调耗时 | 5.21 ms |
| 当前帧解码完成到 SDK renderer | 0.078 ms |
| 发送桥接队列最大等待 | 0.0035 ms |

受影响帧是普通 delta 帧，包序号集合完整。**该事件的停顿位于发送进程交给系统之后、接收桥接收到之前，不能归因于本次关键帧突发或应用桥接队列积压。** 这里的 OS 接受并不代表已实际发到物理网络；两台设备的裸时钟没有直接相减。

为继续区分网络到达与接收进程调度，新增 Darwin 内核收包时间戳。完整 15 分钟测试的保留尾段中，一个 104.24 ms renderer 尖峰的发送间隔约 19.15 ms，接收内核间隔约 104.47 ms；内核到桥接约 0.21–1.12 ms，当前帧解码约 5.27 ms，主流包序号完整。这说明**该尾段尖峰在进入接收应用前已形成**，不是应用队列多等了 100 ms。

这尚不能区分 Surge 内部排队、发送端系统调度、底层 Wi-Fi / 网络和外层隧道。内核观测点是 IP 栈交付，不能冒充物理网卡或 Ponte 外层到包时间。最早 213 ms 事件没有内核戳，不能把后续 104 ms 事件当作同一次冻结来拼接因果链。逐帧环有容量上限；没有保留的阶段明确标为未知。

## 内存结论与中断记录

完整 15 分钟这轮，在第 5 分钟后 footprint 没有继续线性增长：发送端斜率 −0.198 MiB/min，接收端 −0.043 MiB/min；接收端最后五分钟中位数约 41.83 MiB。这支持本轮有限历史和 trace 环的内存进入平台期，不能外推为所有设备、全部运行时长都不存在泄漏。

原统计历史默认最多 3600 条、每秒一条，达到上限前本来就会保留更多诊断对象。本轮新增可控容量和完整异步 journal，计划关闭 trace 后对比 3600 / 300。**正式同条件 A/B 未完成，所以目前不能确认旧增长中有多少来自统计历史，更不能宣布媒体内存问题已修复。** 正常默认历史容量仍为 3600；没有依据残缺 A/B 擅改产品默认值。

| 排除的轮次 | 中断原因 | 保留用途 |
|---|---|---|
| `5888b74f7449`，约 570 秒 | Jump 虚拟屏 120 Hz 切到内建屏 60 Hz；guard 终止。旧 Build 11 没有最终 Host 报告 | 部分样本，不能作为完整长测 |

最后一轮源回调、提交和编码计数接近，接收端没有独立丢掉一半帧。后续不接编码 / 网络的原始捕获短探针为约 59.23 fps；完整 H.264 本机回环 40 秒为约 57.76 fps / 17.55 Mbps。它们是先后诊断观察，运行环境并非严格单变量，不能据此断言某个投屏 App、缩放模式或编码器是唯一根因。

后续[显示模式排查](显示模式自动变化排查.md)已找到调用方：00:33 由 Jump 会话连接关闭后清理虚拟屏；00:37、01:08 等六次实际模式变化由 `UURemoteServer` 提交系统显示配置，包含本轮 47.95 Hz 和 59.94 Hz 中断。三次 UU 停止捕获后约 28.1 秒又恢复原模式，支持“开始捕获套用模式、结束后延迟恢复”的解释；具体控制端触发条件仍未核实。这项归因解释显示条件变化，不证明其他到包尖峰或内存问题也由 UU 导致。

## 本轮实现与验证

- 一次冻结保存一对有界现场，按 RTP 身份关联；不保留像素或报文载荷，不由远端启用 trace。
- 显式 socket trace 增加 `SO_TIMESTAMP_MONOTONIC`；普通无 trace 的收包路径保持 `recvfrom`。缺失和无效戳不伪造。
- 长测统计异步队列最多 8 条、私有 JSONL、完整性校验与报告重建；300 条内存历史也能保留全程证据。
- CLI 收到 SIGTERM 正常关闭 journal、导出 trace 后失败退出。被 guard 停止仍是无效轮次，不包装成通过。
- 新增本机 socket 队列延迟验证、解析与时钟换算、完整 / 缺失 RTP 对齐、journal 容量 / 丢记录 / 关闭验证；相关 Swift 和 Python 测试通过，Mac universal 与 iOS Build 12 编译通过。未向手机安装或上传此诊断构建。

下一步仍是固定同一显示条件、先确认真实源能稳定供帧，再完成关闭 trace 的 3600 / 300 各 15 分钟对照及连续 30 分钟复测；若重新出现超过 200 ms 的到包停顿，保留同一事件的双端和内核时间戳，再做相同桥接的 LAN / Ponte 对照。当前不增加播放缓冲来遮掩尖峰，也不删掉失败轮次。
