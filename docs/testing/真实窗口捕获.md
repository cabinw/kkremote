# 真实窗口捕获与 1440p60 验证

日期：2026-11-13。此轮将 Mac 发送源接到 ScreenCaptureKit，测试真实浏览器文档滚动和视频播放。客户端沿用构建 5 的 H.264 High 5.1、固定 UDP v2 / socket 协议；没有修改信令、SRTP 或配对方式，也没有重新上传 iOS 构建。

## 实现范围

- 通过 Mac UI 的“刷新窗口”或 CLI `--list-windows` 明确选择一个窗口；使用 `SCContentFilter(desktopIndependentWindow:)`。窗口不可用时报错，不自动改抓整个屏幕或其他窗口。
- 使用原生像素缓冲，BGRA / sRGB / SDR，输出 2560×1440，保持宽高比。系统鼠标与点击效果配置为关闭，阴影不计入捕获；应用自身绘制的指针或自动化叠层不属于系统鼠标，仍可能进入图像。
- 捕获队列深度 3；只提交状态为 `complete` 且时间戳单调的帧。直接用 `RTCCVPixelBuffer` 包装捕获缓冲，不增加无界帧队列。
- 捕获跟随显示节拍，WebRTC 源统一限制 60 fps。内容静止时 ScreenCaptureKit 可以减少更新，不能把静态内容低 fps 计为丢帧。
- 报告 schema 5 增加来源类别、捕获完成 / 空闲 / 无效帧计数、源点尺寸及像素倍率、回调间隔、WindowServer 时间到捕获回调的间隔。报告不包含窗口 ID、标题或视频内容。`--list-windows` 的输出则含窗口选择信息，应留在本机。
- `--frame-preview` 是显式启用的 Mac 接收端诊断：仅保留最近一个解码帧，在测量结束后写 PNG。普通会话不保存图像。

窗口输入、关联弹层管理、几何版本、移动端留白 / 边框 / 布局、音频、HDR / HEVC 仍不在本轮范围。窗口改尺寸后保留既定输出并适配宽高比；本轮只验证固定尺寸。

## 捕获节拍修正

首次 CLI 启动在建立 `SCContentFilter` 时触发 WindowServer 初始化断言。CLI 入口已初始化 `NSApplication.shared`，带签名的 Release 应用随后能够正常捕获。

初始同时设置 ScreenCaptureKit `minimumFrameInterval = 1/60` 与 WebRTC 源 60 fps 限制。35 秒 Chrome 滚动短测中，捕获、进入编码器和接收解码都只有约 **56.44 fps**，没有接收冻结；浏览器自身的 rAF 计数对照约 59.93 fps。因此差距已发生在捕获阶段，不能归因于网络。

改为 `minimumFrameInterval = .zero`，由 ScreenCaptureKit 跟随显示刷新、WebRTC 源控制最终输出。40 秒短测中，源 / 编码 / 解码计数速率均约 **59.93 fps**，实际视频约 **2.85 Mbps**，接收 fps 样本 59–60，冻结 0。此修正避免在两个不同调度层上同时卡精确的 1/60 边界；其收益已在当前设备测得，其他刷新率和热状态仍需验证。

Ego 的隐藏任务空间窗口能够被枚举，但测试中没有持续的完整捕获帧。正式用普通 Chrome 的独立窗口测试，窗口中只有本地测试页面。

## 测试条件与结果

源窗口固定 1280×720 点、倍率 2；捕获与实际 H.264 解码均为 2560×1440。视频码率上限 20 Mbps，目标 60 fps，interactive pacing，固定 UDP v2、socket、receive depth 16。

浏览器负载及素材来源见 [fixture 说明](../../Tests/Fixtures/window-capture/README.md)。滚动是真实 HTML / CSS 排版与 scrollTop 更新；视频是 3840×2160、60 fps 的 Big Buck Bunny 无声片段。视频在浏览器内容区等比显示，浏览器工具栏与测试按钮会占用面积，因此不是视频画面铺满 2560×1440。所有本机回环结果都同时运行真实捕获、编码、媒体传输和解码，但不能代替异地 Ponte 测试。

两分钟滚动本机回环已完成（前 10 秒暖机排除）：实际解码 **59.94 fps**，平均视频 **2.94 Mbps**，接收每秒 fps 样本 59–60，丢包 / NACK / SDK 冻结 / 解码丢帧均为 0。平均编码 **8.60 ms**、解码 **2.18 ms**、抖动缓冲 **12.99 ms**；接收回调最大间隔 **55.05 ms**。因此“没有 SDK 冻结”并不等于每一帧严格等间隔。

原始计数汇总见 [机器可读数据](data/2026-11-13-window-capture-summary.json)。两分钟视频本机回环实际解码 **59.93 fps**，平均视频 **5.10 Mbps**（最高约 **18.53 Mbps**），平均编码 **8.55 ms**、解码 **2.33 ms**、抖动缓冲 **23.56 ms**，接收最大回调间隔 **45.02 ms**。丢包 / NACK / SDK 冻结 / 解码丢帧均为 0。浏览器播放会产生少量本地视频掉帧，传输稳定并不能修复源视频已经缺失的画面。

构建 5 已在异地 iPhone 经 Ponte 接收真实 Chrome 窗口，用户确认“已连接，有画面，滚动流畅”。手机端 JSON 及端到端延迟仍未取得。滚动稳定会话排除最初 600 个编码帧后，57 秒主机观察得到 **59.93 fps**、视频平均 **2.86 Mbps**、控制 RTT 平均 **16.62 ms**、发送等待平均 **0.025 ms**；NACK / PLI / 重传包 / 控制探针超时均无增加。断开重连分别记录，不把会话间隔算作冻结。视频阶段随后发现源帧率下降，排查与复测见下。

## 异地视频的 48 Hz 上限与复测

手机第一次视频反馈是“最高48fps未见卡顿”。主机同时观测到捕获源下降到约 30–48 fps，进入编码器与编码完成计数一起下降，未见 NACK / PLI / 重传增加。浏览器保持 visible；约 29.67 秒对照中，视频解码计数约 60 fps，但 rAF 与视频呈现回调约 47.96 fps。

系统显示信息随后报告约 47 Hz，系统设置明确显示固定 **47.95 Hertz**。这是真实显示源的约束，不能要求该源提供 60 个不同显示帧。用户批准把当前 Mac 显示刷新率改为 **60 Hertz**；既有捕获会话在刷新率变更后没有马上恢复 60 fps，因此按原窗口和协议重建捕获会话，配对码与客户端均未改变。重连后主机捕获 / 编码恢复约 60 fps，手机确认“约 60 fps，流畅”。

排除编译 / 功能检查及随后 10 秒后，取 120.00 秒主机视频段：捕获 / 编码均约 **58.87 fps**，实际平均 **5.08 Mbps**，控制 RTT 平均 **16.33 ms**。每秒 fps 样本范围 **40–60**，其中 **14** 个样本低于 58；NACK / PLI / 重传 / 探针超时均无增加。较低的样本中，捕获完成计数和编码计数一起下降，剩余问题仍在源 / 捕获节拍。手机反馈流畅，但严格“每秒稳定 60 fps”的长期目标尚未验收。

此轮验证了固定 60 Hz 条件下的窗口源；**运行中切换显示刷新率的自动处理尚未实现**。目前的恢复步骤是重建捕获会话，尚未把动态显示变化的检测与 SCStream 更新做成产品逻辑。长测中主机显示模式为何变为 47.95 Hz 未确定，不把它归因于 Ponte 或编码器。

Mac Release 与 iOS Simulator 编译通过；真实窗口常驻主机通过两次有效媒体重连、错误密钥拒绝、密钥不变及分会话报告检查。构建检查及额外重连测试的时间段被标记排除，不用于异地性能统计。未上传新 TestFlight 构建。

## 复现

先启动本地 [测试页面服务器](../../scripts/serve-capture-fixture.py)，在独立的普通浏览器窗口打开页面。Mac 应用首次使用需要 macOS 屏幕录制授权；不要通过修改 TCC 数据库绕过授权。

```bash
scripts/build-lab.sh mac-release
.build/DerivedData/Build/Products/Release/KKRemoteLabMac.app/Contents/MacOS/KKRemoteLabMac --list-windows
python3 scripts/benchmark-media.py --window-id SELECTED_ID \
  --rates 20 --duration 120 --resolution 2560x1440 \
  --bridge-transport socket --frame-preview
```

将 `SELECTED_ID` 替换为刚列出的测试窗口 ID。先选择“文档滚动”测试；完成后选择“60 fps 视频”，确认实际开始播放，再执行同一命令。测量时不要同时编译、跑其他媒体基准或改变窗口尺寸。基准默认排除前 10 秒暖机；用相邻首末累计帧数差除以时间差计算实际 fps，单独保留 SDK 的每秒 fps 样本。

真实窗口的重连回归可运行 `python3 scripts/test-persistent-host.py --window-id SELECTED_ID`；脚本使用独立端口与临时密钥，不改常驻手机测试配对文件。

异地复测只更换 Mac 源，在原常驻主机命令中添加 `--window-id SELECTED_ID`。保持原配对文件与网络配置，iPhone 构建 5 可继续接收；配对码和私有地址不写入报告。

## 指标边界

编码、解码、发送等待、抖动缓冲分别报告；这些间隔不能直接相加作为严格端到端 P95。WindowServer age 仅到主机捕获回调，控制消息 RTT 也不是画面延迟。接收回调间隔不等于屏幕实际亮起时间。

解码 PNG 可以判断文字、线条和画面缩放是否明显异常，不能代替帧对齐的 SSIM / VMAF 或远端设备上的清晰度验收。真正输入到显示延迟仍需同步时钟 / 光学方法及交互源；本轮不实现远程输入。
