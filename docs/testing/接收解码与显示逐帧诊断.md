# T02c：接收解码与显示逐帧诊断

2026-11-13。通信侧实现，USB 安装本地构建 9。继续使用原 Ponte 地址、端口与配对信息；客户端布局和交互由 iOS 会话维护，本次不改交互代码，也未上传 TestFlight。

## 新增记录

`FrameTrace` schema 3 在接收端接上以下阶段：

`RTP ingress → decodeSubmit → decodeVTSubmit → decodeVTOutput → decodeOutput → displayInput → displayMainDequeue → displayEnqueue`

- 解码 wrapper 覆盖 HEVC 和 H.264；HEVC 内部另记 VT 提交 / 异步输出。用同一媒体 epoch、唯一 RTP timestamp 与递增解码输入 ID 关联，不使用相邻时间推测。H.264 SDK 不暴露 VT 内部阶段。
- Annex-B、参数集、等待关键帧、会话创建、block / sample 创建、VT 同步 / 异步错误、frameDropped、空输出、像素格式不符分别计数。重复 timestamp、超过 2 秒未匹配、超过 120 个待关联输入记 unknown，不直接宣布解码丢帧。
- `ReceiverTelemetry` 汇总到 `LabSample.receiverDetails`，报告 schema 9。解码 P95 和主线程等待 P95 使用最近 600 次；离线 trace 分析可覆盖完整保留区间。
- 每个显示视图绑定独立 `observerID`，记录 latest 替换、主线程取出、显示背压、格式 / sample 失败、enqueue、停止取消与迟到回调。`Binding` 代次令旧轨道回调和旧调度闭包不能进入新视图队列；旧引擎停止也不会停止已经重绑到新引擎的视图。
- `PresentationDiagnostics` 以弱引用的精确 `RTCVideoTrack` 对象找到所属记录器，不改客户端的视图 API。独立的 FrameCounter renderer 与实际显示视图是两个并行观察者，不能把二者先后回调的差当作显示耗时。
- `displayEnqueue` **只表示提交给 AVSampleBufferDisplayLayer，不代表屏幕扫描输出或物理显示时刻**。没有因此声称端到端延迟。

默认关闭逐帧 trace。iOS 通过本地启动参数 `--media-diagnostics-run <安全目录名>` 保存报告，额外加 `--media-frame-trace` 才记录逐帧数据；前台正常停止后写入 `Documents/TransportDiagnostics/<目录名>`。不新增远程开启诊断的接口，不改变配对与网络设置，不记录媒体载荷或用户输入。汇总采样可能比停止时刻早约一秒，最终队列取消以 trace 为准。

## iPhone 蜂窝 Ponte 对照

iPhone 15 Pro Max，状态栏确认蜂窝 5G，Surge Ponte；USB 只用于安装、操作镜像和回收报告。1440p / 60 fps / 20 Mbps 上限，HEVC Main10 PQ，固定 UDP v2 / socket、realtime 播放策略。Ponte 外层实际通道仍未知。

真实 Chrome 窗口显示持续移动的密集 SVG 图纸（2× 速度）。源窗口 1681×1084 点、2× 密度，保持比例适配到 2560×1440；图纸本身是 SDR 内容，不替代 HDR 母版色彩验收。前台 UI 相同，没有并发编译或运行其他媒体基准。

按 2 秒 → 10 秒 → 2 秒顺序复核；该秒数实际配置为 120 / 600 帧的最大周期，按需关键帧与 NACK/RTX/PLI 均保留。整段稳态解码平均分别为 60.00 / 59.98 / 60.00 fps，实际视频平均 10.95 / 11.55 / 11.49 Mbps，三轮 SDK 冻结、解码丢帧和最终 RTP 丢包均为 0。

两轮 2 秒基线各运行约 79 秒，事件环覆盖了最早约 10 秒；10 秒轮约 62 秒，没有覆盖。为避免时长不等，下面仅比较每轮停止前留出 2 秒余量、完整保留的 **50 秒**，不掩盖原始覆盖计数。窗口边界可能缺少个别帧的更早阶段，分析器不会补造关联。

| 相同 50 秒区间 | 2 秒基线 | 10 秒策略 | 2 秒复核 |
|---|---:|---:|---:|
| 解码输出 / 秒 | 60.00 | 59.98 | 59.98 |
| 应用 enqueue / 秒 | 58.98 | 59.72 | 59.60 |
| latest 替换 | 51 | 13 | 19 |
| enqueue 间隔 >50 ms | 42 | 23 | 31 |
| enqueue 间隔 >100 ms | 2 | 2 | 1 |
| enqueue 间隔 P95 / max，ms | 34.13 / 132.22 | 32.50 / 121.09 | 33.36 / 104.53 |
| 解码回调 P95，ms | 4.60 | 4.52 | 4.69 |
| 主线程等待 P95，ms | 0.087 | 0.082 | 0.082 |
| 显示背压 / 显示失败 | 0 / 0 | 0 / 0 | 0 / 0 |

10 秒策略减少周期性突发，50 ms 以上间隔和 latest 替换都少于两轮基线；但蜂窝网络随时间变化，最大间隔没有一致改善，不能把三轮差值宣布为固定收益。SDK 约 60 fps 也不能直接写成每秒 60 帧都提交显示。本轮没有长冻结可用于比较修复速度；T02b 的受控丢包结论仍仅适用于当时的回环实验。

随后关闭两端逐帧 trace，以 10 秒周期继续同一窗口约 **350 秒**。剔除启动后前 5 秒的稳态区间为 343 秒，解码 **59.997 fps**、实际视频平均 **11.966 Mbps**；最后汇总累计解码 20,963 帧，SDK 冻结、解码丢帧、最终 RTP 丢包、NACK、PLI 均为 0。显示收到 20,963 帧、enqueue 20,694 帧、latest 替换 269 帧；没有显示背压或错误。这里 0 次 SDK 冻结不等于没有短时帧间隔尖峰。

该轮控制 RTT P50 / P95 为 35.96 / 45.47 ms，每秒接收缓冲均值的 P95 为 10.07 ms；末次最近 600 帧解码回调 P95 为 4.46 ms、主线程等待 P95 为 0.119 ms。两个百分位的采样口径不同。观测开 / 关均约 60 fps，但这不是隔离网络条件的开销实验，也未测 CPU / 能耗，不能据此宣布诊断零开销。实际载荷没有持续打满 20 Mbps，T01 的持续 15–20 Mbps 压力门槛仍未通过。

脱敏统计、相同 50 秒窗口结果与原始 trace SHA-256 见 [实验数据](data/2026-11-13-receiver-frame-trace.json)。原始报告与逐帧文件只保存在本机和测试设备，不进入仓库；数据不含端点、窗口标题、配对信息或媒体载荷。

## 两类长间隔已分开

旧策略的一次 132.24 ms renderer 间隔对应 283,565 字节关键帧。相邻编码输出相隔 19.92 ms，首包相隔 20.11 ms；关键帧发送展开和收齐时间拉长了后续解码输入。桥接本身每帧最大等待 P95 约 0.004 ms，不能据此归咎于应用 Ponte 桥接队列积压。

新策略仍有一次 **121.09 ms enqueue 间隔**，对应普通增量帧（32,038 字节、28 包）：

- 发送端这 28 个包在约 **1.12 ms** 内进入桥接；接收端同样 28 个原始包却分散在约 **103.51 ms** 内到达，序号完整，无应用桥接丢弃。
- 接收端首包到 decodeSubmit 为 **106.58 ms**，末包到 decodeSubmit 约 **3.07 ms**。
- 解码提交到回调约 **3.69 ms**，主线程等待 **0.049 ms**，显示准备约 **0.669 ms**。
- 该帧接收桥接的最大内部停留约 **0.113 ms**，发送桥接队列最大等待约 **0.003 ms**。

这将这次尖峰定位在两端应用桥接观测之间的包到达展开，排除了本次解码器与应用显示队列长时间积压。仍无法细分是 OS、Ponte 外层、蜂窝链路还是外部调度；也不能把两台机器绝对时间直接相减求单向网络延迟。保留 NACK/RTX，不因这次最终无丢包而关闭恢复机制。

## 重现

```bash
bash scripts/test-receiver-trace.sh
bash scripts/test-hdr-renderer.sh
bash scripts/test-main10.sh
python3 scripts/analyze-receiver-trace.py <receiver-trace.json> --last-seconds 50 --output <analysis.json>
python3 scripts/analyze-rtp-trace.py <sender-trace.json> --receiver <receiver-trace.json> --output <rtp-analysis.json>
```

Mac Host 沿用现有 CLI 参数，用 `--hevc-keyframe-seconds 2|10` 对照；短测加 `--frame-trace-dir <沙盒目录>`。每轮独立进程和诊断目录。iOS 通过 devicectl 启动同一 bundle 并附加上述诊断参数，前台点击连接与断开，用 appDataContainer 回收文件。端点和配对信息由原本本地配置提供，不放入报告。

测试覆盖 RTP 回绕、碰撞、超时、有界待关联表、具体 HEVC 失败不重复计数、latest 替换、停止取消、旧 generation 闭包不污染新队列、旧引擎不停止已重绑视图，以及分析器的多 SSRC / 重复输入 / 缺少身份拒绝关联。硬件探针 180 帧全部 Main10 解码和 enqueue，0 背压、0 显示错误。

发送端 FrameTrace / EncoderTelemetry、RTP 解析与分析器的现有回归也通过。H.264 1440p60 回环 12 秒通过，trace 精确匹配 720 次解码输入 / 输出，无解码错误；停止前最后一秒汇总为 719 帧，末尾 1 帧由 trace 补齐。Mac / iOS Release 均构建成功；构建 9 只通过 USB 安装到本机连接的 iPhone，没有改内部 TestFlight 分发。

T02c 实现与蜂窝关键帧复测已落地；完整 T02 / T06 仍需受控丢包下的真机恢复、静态源边界、更多观测开销复核和物理显示延迟测量。短测与后续分钟级观察均不替代 30 分钟稳定性验收。

完成后已恢复原 HDR 视频 / 灰阶循环窗口，Mac 使用新通信实现与 10 秒周期，手机按正常方式启动并重连；原地址、端口与配对信息保持不变，逐帧日志关闭。
