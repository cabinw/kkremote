# iPhone 蜂窝 Ponte · USB 构建 12 复测

2026-11-14，手机重新接入 USB 并解锁后，安装已有构建 12，完成一次 180 秒连通性检查和一次 600 秒真实窗口压力测试。原连接地址、端口、配对码保持不变；没有修改客户端交互或上传 TestFlight。脱敏数据见[本轮摘要](data/2026-11-14-iphone-build12-ponte.json)。

600 秒轮次通过现行传输检查：实际解码 59.987 fps、11.829 Mbps，SDK 冻结和解码丢帧均为 0。手机内存在本轮进入约 91 MiB 平台。这个结果不能替代 30 分钟验收，也不能消除前一轮已经记录的冻结。

## 配置与有效性

- iPhone 15 Pro Max，USB 供电；界面确认蜂窝 5G，固定 UDP v2 / socket，通过已有 Ponte 端点连接。外层 Ponte 路径类型仍未知，USB 用于安装、控制和读取报告。
- 两端 Release 构建 12；2560×1440、60 fps、20 Mbps 编码预算；实际协商 HEVC Main10、10 位 PQ。Host 使用 interactive / realtime、10 秒周期关键帧、捕获深度 3、桥接接收深度 16，故障注入关闭。
- 捕获真实 Chrome 窗口，1280×720 点、2× 像素；四面板确定性 SVG 图纸以 3× 速度持续平移和缩放。图纸本身是 SDR 内容；这轮验证 Main10/PQ 传输，不重做 HDR 母版亮度与色准验收。
- 两端开启有界逐帧 trace，统计历史容量 3600。手机不支持本轮 CLI 的异步 journal；600 秒逐秒记录全部保留。
- 源身份守护有效并正常结束，覆盖 680.512 秒；窗口尺寸、显示模式 3456×2234 / 60 Hz 保持一致。守护每 10 秒采样，不能证明采样之间绝无瞬时变化。
- 开始操作后约 45 秒关闭 Device Hub 投屏预览，其余时间手机独立前台运行；不能称整个测试从未启用 USB 镜像。全轮源帧率约 59.99 fps。

## 600 秒真实窗口结果

手机末次逐秒样本在 599.047 秒，有效媒体观察约 598 秒；Host 报告含连接前等待，不能用总运行时间直接除媒体帧数。自动检查的名义时长为 600 秒，全部检查通过。

| 指标 | Mac Host | iPhone Viewer |
|---|---:|---:|
| 稳态编码 / 解码帧率 | 59.988 fps | 59.987 fps |
| 实际视频码率 | 11.832 Mbps | 11.829 Mbps |
| 应用 UDP 封装吞吐 | 12.589 Mbps | 12.587 Mbps |
| 桥接 pending 最大值（逐秒） | 0 | 0 |
| 桥接累计最大等待 | 0.037 ms | 0.426 ms |
| App CPU 中位数 | 13.44% | 33.69% |
| 5 分钟后 footprint 中位数 | 39.67 MiB | 90.95 MiB |
| 5 分钟后 footprint 线性斜率 | −0.004 MiB/分钟 | −0.162 MiB/分钟 |
| 热状态 | nominal | nominal |

20 Mbps 是预算，实际负载没有持续占满预算。UDP 封装吞吐不含 IP 和外层 Ponte 开销；CPU 的 100% 表示一个核心，不含 WindowServer、Chrome 和 Surge。

手机末次样本累计解码 35,891 帧，SDK freeze、framesDropped、NACK、PLI 均为 0；解码 pending、失败和匹配溢出也为 0。显示观察器在该样本中 received / enqueued 均为 35,891，replacement / backpressure / failure 为 0。

**逐秒报告没有覆盖停止前的全部尾帧。** 最终 trace 另有停止前约 44 ms 内的 3 次 `latest_replaced`，以及停止时 1 次 `media_stop_pending`。因此只能说末次统计样本中显示丢帧为零，不能宣称完整 trace 零显示丢帧。停止边界与导出调度需另行核查，现行传输检查器也不包含这个显示尾段关口。SDK 冻结/解码丢帧与显示替换是不同计数。

手机 30 秒后 footprint 为 89.30–102.44 MiB，有短时峰值后回落；本轮未见持续单调增长。10 分钟、trace 开启、USB 供电的结果不能证明长期无泄漏，也不能完成历史容量 300/3600 的因果 A/B。

## 关键帧间隔的逐帧证据

接收 trace 是有界尾段，覆盖 4096 个解码输出，约最后 68 秒。该段 SDK renderer 间隔 P50 / P95 / 最大为 16.60 / 24.31 / 82.98 ms；解码回调 P95 为 4.19 ms。这里是 SDK 回调，不是物理屏幕呈现时间，也不是端到端延迟。

最大的六个间隔均落在关键帧上，约 71–83 ms。按同一 primary SSRC、RTP 时间戳和完整包序号集合对齐，最大一次表现为：

| 相邻帧阶段间隔 | 数值 |
|---|---:|
| 发送端首包被 socket 接受 | 16.62 ms |
| 发送端末包被 socket 接受 | 68.80 ms |
| 手机首包内核到达 | 17.95 ms |
| 手机末包内核到达 | 87.70 ms |
| 当前帧最后一包进入桥接 → 提交解码 | 1.08 ms |
| 当前帧提交解码 → 输出 | 5.14 ms |
| 当前帧解码输出 → SDK renderer | 0.10 ms |

发送端末包间隔已经扩大，应用桥接等待仅 0.0013 ms，adapter residence 最大 0.038 ms；瓶颈不表现为该桥接等待队列积压。证据指向关键帧分包发送节奏，接收路径又有附加抖动。仍需把编码完成、WebRTC pacer 出包、实际帧大小接起来，才能精确区分编码与发送调度贡献；不能仅凭这些间隔认定全部由 pacer 引起。

## 180 秒检查中的冻结不能略去

初始 HDR 循环页面的影片区域为黑，灰阶阶段可见，实际流量仅 0.698 Mbps；它不是有效高负载或新 HDR 影片验收。手机收到 2 次 SDK freeze，平均 58.965 fps。源黑画面的原因本轮未定位，不据此判定 Main10 链路故障。

首次冻结现场匹配到一对相邻 delta 帧，包序号集合完整：发送端 socket 接受间隔 17.80 ms，手机内核到达间隔 1523.32 ms，SDK renderer 间隔 1527.04 ms；该帧解码 5.37 ms，内核到桥接 2.35 ms。

这次约 1.5 秒空档形成在发送端 socket 接受之后、手机内核交付之前，不是手机解码耗时造成的。socket 接受不代表物理发出，内核交付不等于外层隧道到包；尚不能继续区分发送端系统、Surge 外层、蜂窝网络或手机网络栈。零 NACK / PLI 不能排除整段流量被延后。另一次冻结没有独立的首次现场快照，不套用第一次的归因。

该轮结束后才切换到高负载页面，旧 guard 因标题改变失效；不拿它作为完整素材守护通过轮次。保留冻结现场作为诊断证据。
